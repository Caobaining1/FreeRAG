# 硬件加速：首次启动扫描与分平台后端选择

## 0. 要解决的问题

同一份代码要发给 Mac、Windows、Linux 三种桌面端用户，但**当前后端选择是写死的**：

| 流程 | 现在跑在哪 | 代价 |
| :-- | :-- | :-- |
| 版面分析 / 表格结构（ONNX） | **CPU**，默认写死 | 已实测：60 文档 234 页，CPU 8.99 s/文档 vs CoreML 1.43 s/文档，**慢 6.3×** |
| Laya 决策模型（ONNX） | **CPU**，硬编码 | 同上，且它没接 provider 设置 |
| 图表转译（PyTorch） | MPS 上强制 fp32 | 已实测修复：118 s → 52 s（2.3×） |
| 生成 / 通用视觉（Ollama） | `ollama serve` 默认参数 | 没有按显存设置 GPU 卸载层数与 flash-attn |
| 嵌入 | SiliconFlow 远程 API | 无本地加速空间，只能靠批量与缓存 |

`sidecar/layout_onnx.py` 的注释把这件事说得很直白：

> `"cpu" is still the default only because it was asked for explicitly; flipping it is this line.`

也就是说，最大的一笔加速不是新功能，而是**把已经写好、已经量过的开关打开**——前提是它只在真正有加速器的机器上打开。这就是为什么需要"首启扫描"：不能靠猜平台，得实测。

## 1. 扫描什么

分两级。轻量探测在桌面端（Node）做，因为内核还没起来、而这些结论要用来决定怎么拉起内核；重量级实测在内核侧做，因为只有加载了运行时才知道它到底能提供什么。

### 1.1 桌面端快扫（Node，`desktop/main.js`，约 100 ms，不含子进程）

* **OS 与架构**：`process.platform` / `process.arch`（darwin-arm64、darwin-x64、win32-x64、linux-x64）
* **CPU**：`os.cpus()` 型号与核数（识别 Apple M 系列 vs Intel）
* **内存**：`os.totalmem()`——决定 7.4 GB 图表模型能不能加载、以及并发数上限
* **加速器存在性**：
  * macOS：Apple Silicon 一律有 Metal；Intel Mac 需判断是否独显
  * NVIDIA：`nvidia-smi -L` 是否可执行（顺带拿到显存）
  * AMD：`rocm-smi`
* **磁盘**：模型目录所在卷的剩余空间（决定能否下载模型）

结果作为环境变量交给内核（`kernelEnv()` 里已有的注入点），并缓存到 `userData/hardware.json`。

### 1.2 内核实测（Go + 子进程，首次启动，约 1–2 s）

存在性不等于可用。真正的判据是问运行时自己：

* **onnxruntime**：`onnxruntime.get_available_providers()`（sidecar Python）→ 是否含
  `CoreMLExecutionProvider`（macOS）、`CUDAExecutionProvider`（NVIDIA）、`DmlExecutionProvider`（Windows）
* **PyTorch**（图表服务）：`torch.cuda.is_available()` / `torch.backends.mps.is_available()`
* **Ollama**：`/api/version` 可达性，以及 `ollama ps` 报告的模型是否 `100% GPU`

三条都必须**真的跑一次最小推理**才算数（见 §4"回退"）：编译型后端（CoreML）首次编译很慢且**并发编译会互相排队**，实测注释里记着 4 个进程同时编译花了单进程的 4 倍时间——所以预热必须串行。

### 1.3 缓存与重扫

* 首次扫描结果写入 `userData/hardware.json`，带 `schemaVersion` 和 `scannedAt`
* 仅在文件缺失或版本变化时全量扫描；否则直接读缓存，启动不付代价
* 设置页提供「重新扫描硬件」按钮；用户手动指定的后端（§4）优先于扫描结论
* 扫描结论通过一条 JSON-RPC 上报给 UI，设置页显示「加速：Metal (CoreML) / CUDA / 仅 CPU」——用户能看见自己拿到了什么

## 2. 能力矩阵：平台 × 流程 → 选什么后端

| 流程 | 运行时 | Apple Silicon | Intel Mac | NVIDIA (Win/Linux) | 无加速器 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 版面分析 / 表格结构 | onnxruntime | **CoreML** | CoreML / CPU | **CUDA** → Dml | CPU |
| Laya 决策模型 | onnxruntime | CoreML | CoreML / CPU | CUDA → Dml | CPU |
| 图表转译（1.7B） | PyTorch | **MPS + fp16** | CPU fp32 | **CUDA + bf16** | CPU fp32 |
| 生成 LLM | Ollama / llama.cpp | Metal（全量卸载） | CPU | CUDA（全量卸载） | CPU，线程=核数 |
| 通用视觉 VLM | Ollama / llama.cpp | Metal | CPU | CUDA | CPU |
| 嵌入 | 远程 API | — | — | — | 批量 + 缓存 |

要点：

* **ONNX 侧**：`auto` 已经实现了「按 `get_available_providers()` 排序，并以 CPU 兜底」（`sidecar/layout_onnx.py` 的 `default_providers()`）。所以三平台共用一条逻辑，不需要为每个平台写分支——把默认从 `cpu` 改成 `auto` 即可。
* **图表侧**：`pick_dtype()` 已经按设备选（CUDA→bf16、MPS→fp16、CPU→fp32）。剩下的是**内存门槛**：7.4 GB fp32 / 3.7 GB fp16，内存不足时应当直接不启用图表后端，而不是 OOM。
* **Ollama 侧**：我们只通过 `FREERAG_OLLAMA_URL` 连一个已有服务（`scripts/setup-ollama.sh` 用默认参数 `ollama serve` 拉起），所以加速只能从两个地方施加——Modelfile / 服务启动参数，以及每次请求的 `options`（当前只有 `num_ctx`/`num_predict`/`temperature`，**没有 `num_gpu`**，这是要补的）。

### 2.1 前提：加速运行时必须先装进包里

`auto` 的语义是「从 `get_available_providers()` 里挑，挑不到就退化到 CPU」。它**不会报错**——所以如果包里的 onnxruntime 根本不含某个 EP，扫描会安静地给出"仅 CPU"，用户完全看不出自己没加速。这是"不同系统自动加速"能否成立的硬前提，必须在打包侧解决：

| 系统 | 需要的 ORT 包 | 现状 | 后果 |
| :-- | :-- | :-- | :-- |
| macOS | `onnxruntime`（官方 wheel **自带 CoreML**） | ✅ 已满足（实测 1.30：`['CoreML', 'Azure', 'CPU']`） | `auto` 直接生效 |
| Linux + NVIDIA | `onnxruntime-gpu` | ✅ 新增 `requirements-cuda.txt`（opt-in，见下） | 默认仍是 CPU；要 CUDA 得显式选 |
| Windows | `onnxruntime-directml` | ✅ `requirements.txt` 用 PEP 508 平台标记自动装 DirectML 版 | `auto` 可拿到 `DmlExecutionProvider`；构建脚本已补 Windows 三元组（**未真机验证**） |

已落地：`requirements.txt` 里的 onnxruntime 改成两条带 `sys_platform` 标记的声明，每个平台恰好命中一条——在本机用 `packaging` 求值验证过：

```
darwin   -> onnxruntime>=1.17; sys_platform != "win32"
win32    -> onnxruntime-directml>=1.17; sys_platform == "win32"
linux    -> onnxruntime>=1.17; sys_platform != "win32"
```

按平台分档而不是按"这台机器的显卡"分档，是因为安装包是在**构建机**上打的，构建机的显卡跟最终用户的机器毫无关系。CUDA 那条做成 opt-in（`ORT_FLAVOUR=cuda` 或 `requirements-cuda.txt`），因为它是 ~2 GB 轮子对 ~40 MB。

衍生约束：

* **CUDA 版 ORT 要求用户机器上有匹配版本的 CUDA/cuDNN**，而我们不能直接把它塞进安装包（体积与许可都不允许）。所以 Linux 上"检测到 NVIDIA"≠"一定能用 CUDA"，扫描必须实测而不是看 `nvidia-smi` 存在。
* **Windows 优先 DirectML 而不是 CUDA**：DirectML 走系统自带的 DX12，AMD/Intel/NVIDIA 通吃，不需要用户额外装驱动栈，是桌面分发的现实选择。
* 因此依赖要**按平台分档**（`requirements` 分平台，或在 `fetch-python-runtime.sh` 里按 `uname` 装不同 wheel），并且 UI 必须显示"仅 CPU（原因：…）"，否则"自动"会退化成"静默不加速"。

## 3. 分阶段落地

按「收益 ÷ 风险」排序。前一阶段不依赖后一阶段。

### P0 — 打开已量过的开关（改动极小，收益最大）

1. `sidecar/layout_onnx.py`：`DEFAULT_PROVIDER_CHOICE = "cpu"` → `"auto"`。
   预期：Mac 上版面+表格 **约 6.3×**（已实测数据，不是估算）。
2. ~~`sidecar/laya.py`：也换成 `default_providers()`~~ **实测否决，保持 CPU**。
   Laya 每次调用只跑少量 token，加速器帮倒忙：

   | | 建会话 | 单次决策 |
   | :-- | --: | --: |
   | CPU | 1.15 s | **26 ms** |
   | CoreML | 13.56 s | **407 ms** |

   **慢 15×**，且编译还贵 12×。`laya.py` 原有注释推测的正是这件事（"per-call graph upload"），现在换成了实测数字写进代码，避免以后有人再来"优化"它。教训是：同一个 `auto` 不能套给所有模型——版面模型每页算得多（省 7.6×），Laya 每调用算得少（亏 15×）。
3. 保留 `FREERAG_ONNX_PROVIDERS` 显式覆盖（`"cpu"` 仍可用于对照测量）。

风险：CoreML 首次编译有一次性成本，且并发编译会排队 → 必须配 P0 的预热（串行），并把编译缓存目录纳入已有的 session 复用（`session_for`）。

### P1 — 图表按内存与设备决策（大部分已完成）

* ✅ 已完成：MPS 走 fp16（118 s → 52 s，输出逐字一致）
* ✅ 已完成：**内存门槛**——桌面端把扫到的总内存以 `FREERAG_HW_MEMORY_BYTES` 传给内核，内核启动图表服务前检查，不足 12 GB 直接不启用并说明原因。实测两条路径：

  ```
  8 GB  → warning: figure captions disabled: this machine reports 8.0 GB of memory
          and the chart model wants about 12 GB to load without swapping;
          FREERAG_CHART_FORCE=1 overrides this
  16 GB → figure captions: laya-chart-1.7b at http://127.0.0.1:61317 (started by this process)
  ```

  拦在启动前而不是启动后，因为模型装不下不会报错——它会换页，把整台机器一起拖住。
* 待补：CUDA 机器走 bf16（现在分支已写好，但没机器验过）
* 待补：扫描结论决定 `FREERAG_CHART_CONCURRENCY`——实测 MPS 上并发会直接 abort 进程
  （`failed assertion _status < MTLCommandBufferStatusCommitted`），所以 Mac 必须锁 1；
  服务内已有推理锁兜底，但内核侧不该发出并发请求

### P2 — 首启扫描本体 —— 已完成

已落地，本机器实测：

* **桌面端快扫**：`app.whenReady` 里跑一次，结果进 `userData/hardware.json`（带 `schemaVersion`，仅在缺失或换版时重扫），启动日志打印一行
  `hardware: metal · 10 cores · 16 GB`
* **设置页**：显示「本机提供什么」与「模型实际跑在什么」两半，附「重新扫描」按钮
* **内核实测上报**：新增 RPC `hardware`，返回两个 deepdoc session 各自报告的 provider（不是平台推测）
  ——实测返回 `CoreMLExecutionProvider;CPUExecutionProvider`
* **串行预热**：新增 sidecar 方法 `warmup` + 内核后台 `warmDeepdoc`，把编译从第一个文档挪到启动：
  `deepdoc layout session built in 8.8s on CoreML…`（后台，不阻塞 ready）

预热的价值来自一个对照：这笔 8.8 s 原本会算在用户解析的第一个文档头上，且发生在 UI 已经宣告「正在解析」之后——看起来像卡死，而不是一次性开销。

### P3 — 生成与视觉按显存调参

* 请求 options 增加 `num_gpu`（显存够则全量卸载）与 `num_batch`
* `scripts/setup-ollama.sh` 或 Modelfile 层设置 flash-attn、上下文与 KV 量化
* `FREERAG_VLM_CONCURRENCY` / `MAX_SIDE` 按内存与 GPU 定档（现在是固定值）

### P4 — 图表转译换运行时（跨平台统一）—— 暂缓，2026-10-07

**决定：不做。** 记下理由，免得日后重开时从头再想一遍。

盘点过实际工作量，两件事降低了它的吸引力：

* 视觉塔一半已经导好了（`models/layachart-onnx/vision_projector.onnx`，362 MB，实测 11.2 ms vs MPS 66.9 ms），但 **decoder 没导**——`export_onnx.py` 在那一项上只留了句"见下方命令：optimum-cli"。也就是说真正的加速对象（自回归生成）恰恰是没验证过的那一半。
* decoder 是 `Qwen3-0.6B`（`configs/chartvlm.yaml`），架构标准、导出有现成工具，但 **CoreML EP 对动态 shape + KV cache 的自回归 decoder 支持有限**，很可能只卸载部分算子、其余回落 CPU；而 0.6B 在 CPU 上未必比 MPS 快。**有可能折腾完没有收益**，这是决定不做的主因。

代价不是"不能做"而是"不确定值不值"：全套 1–2 个工作日，其中真正的选择点是一小时的探针（导出 decoder + 测 CoreML/CPU/MPS 三个 ms/token）。

**什么时候值得重开**：图表转译变成实际瓶颈（现在 fp16 约 52 s/图，索引时后台跑，能忍），或者出现第二个必须快的场景。届时先做那一小时探针，拿到数字再决定，不要直接投入。

（另：标题里"1.7B"是全模型含视觉塔；负责逐 token 生成的是 0.6B，所以 145 ms/token 的理论上限约 6 ms 而非 17 ms。）

## 4. 探测失败的回退

扫描可能错（驱动坏了、显存不足、运行时版本不含某个 provider）。因此：

1. **链尾永远有 CPU**：`default_providers()` 已经保证列表以 `CPUExecutionProvider` 结尾
2. **实测而非相信**：拿到 provider 名单后跑一次最小推理；失败则降级并记日志
3. **显式覆盖优先**：`FREERAG_ONNX_PROVIDERS=cpu` 等环境变量与设置页选项始终压过扫描结论
4. **失败可见**：降级写入日志，并在设置页显示「已回退到 CPU（原因：…）」，不要静默

## 5. 验收与观测

* 每条加速路径都要有前后对比数字，写进日志（图表侧已有 `transcribe 52.4s, 338 tokens (155 ms/token)`，其余流程照此补）
* 首次启动日志打印一行结论：`accelerator: coreml (layout, tsr, laya), mps+fp16 (chart), metal (llm)`
* 三平台各留一份对照基线：同一批文档、同一张图的端到端耗时

## 6. 未覆盖 / 已知边界

* **嵌入**是远程 SiliconFlow API，本地无模型可加速；只能做批量与缓存（且目前只有这一个 provider）
* **Refrag** 是纯文本压缩（`internal/agent/refrag.go`），不调模型，无需加速
* **Windows / Linux 的实测数据目前为零**——CoreML 的 6.3× 来自 Mac 实测，CUDA 与 DirectML 的收益需要在目标机器上量过才能写进默认值
* P4 的运行时更换是最大的单项收益，也是最大的不确定性，排在最后正是为此
