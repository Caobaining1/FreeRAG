# 并行与加速：测量纪要

本文记录 freerag 在"提速"上做过的全部尝试——**做成了什么、没做成什么、为什么**。
写下来的目的不是总结成绩，而是让下一次有人想"要不并行一下"时，先看到已经试过什么、
以及每条路的**实测结论与机制**。

所有数字都是本机实测（除非明确标注"估算""推理"）。**结论先行**：

| # | 尝试 | 结果 | 一句话机制 |
| :-- | :--- | :--- | :--- |
| 1 | **解析会话缓存**（建一次 · 多篇复用） | ✅ **6.3×**（505.6s → 85.9s / 60 篇） | 构建步骤被塞进了每篇文档的热路径，是重复劳动 |
| 2 | **复杂路径不再生成 N 个子答案** | ✅ 省掉 N 次完整生成（每次约 1 分钟） | 那些子答案的唯一读者是合成 prompt，内容在合并池里已有 |
| 3 | 解析多进程并行 | ❌ **1.0×**（8.0/8.5/8.0s 每篇） | CoreML 编译全局串行，多进程只是排队 |
| 4 | 解析纯 CPU 多进程并行 | ❌ **1.7–2.0× 更慢** | 内存带宽饱和（加线程 = 更挤总线） |
| 5 | 解析多线程（intra-op） | ❌ 1/2/3/4 线程 = 1.9/3.7/5.4/7.4s **每页** | 同上：算子不并行，只增竞争 |
| 6 | **Laya 判定 · sidecar 线程池** | ❌ **无加速**（16 次：7.1/7.5/7.6s @ 1/2/4 worker） | 一个饱和的共享资源，不是核数 |
| 7 | Laya 判定 · 多进程 | ❌ **更差**（两进程 13s vs 单进程 7.1s） | 同上，且各自多占 1.2GB |
| 8 | Laya 判定 · **批量打分** | ❌ **0.56×（慢 1.8 倍）** | 成本按 token 计，不是按前向趟数计，没有东西可摊薄 |
| 9 | 生成（Ollama）并发 | ❌ 0.87×（默认）/ 0.82×（`NUM_PARALLEL=2`） | 单槽排队；开多槽后争同一条总线 |
| 10 | 生成速度本身（7 个旋钮） | ❌ 全部无差别，恒定 **~6.4 tok/s** | 本机环境的固定值，能动的只有 **token 数量** |

**主题一句话**：这台机器上，凡是"同时做更多事"的尝试都**无效或更差**；
真正提速的两次都是**"少做重复的事"**（建一次、别生成）。

## 1. 环境与方法

- **机器**：MacBook Air，M5，10 核（4P+6E），**16GB**，无风扇。
- **常驻**：VS Code + Electron + 内核 + sidecar + qdrant + Ollama（实测这些是否常驻对结果**无影响**，见 §3.1）。
- 复跑脚本见 §7。

### 1.1 四条方法论教训（都是踩过的坑）

1. **跨场次的数字不可比。** 同一份代码、同一份数据、同一批用例（带标注 400 桶），
   Laya 单次判定中位数在两次会话里是 **3.2s 与 0.4s**——差别只在于当时机器的负载
   （内存压力、谁在抢带宽）。**所以本文所有对比都取自同场次、交替测量**；引用跨场次数字时已注明。

2. **噪声下限约 ±20%。** 批量测量里 `rows=1` 那一行跑的是**同一段代码两遍**，
   它给出 0.97×——这就是这台机器的噪声地板。低于 1.2× 的"加速"不要相信。

3. **onnxruntime 的首次 `Run` 有一次性开销。** 同一条判定，首次 1.07s、之后 0.26s
   （执行计划懒构建）。不预热就计时，会得到"8 条逐条比 2 条还快"这种自相矛盾的结果——
   我的第一次批量测量就是这么错的。

4. **缓存会把"改进"变没。** 解析缓存命中时单篇 0.07s，冷跑 8.43s。
   任何"优化前后对比"都必须 `--no-cache`，否则测的是缓存。

## 2. 有效：真正提速的两处

两处的共同点：**都不是并发，而是删掉重复劳动**。

### 2.1 解析会话缓存（6.3×）

**问题**：`pipeline.make_detector()` 每篇文档新建一个 detector，而 `layout_onnx._load()`
只把 ONNX session 缓存在**实例**上。于是每解析一篇文档，就重新构建一次会话。

**代价有多大**（同一模型、两种后端）：

| 后端 | 建会话 | 每页推理 | 每篇（60 篇 / 234 页实测） |
| :--- | ---: | ---: | ---: |
| CoreML（657/681 节点编译给 ANE） | **6.90s** | 0.25–0.39s | 8.43s（其中 **82% 是建会话**） |
| 纯 CPU（1 线程） | **0.14s** | 1.9–2.27s | 8.99s |

**改法**：`session_for(path, providers, cpu_threads)` —— 进程级注册表 + 双重检查锁，
key 是决定"编译产物长什么样"的三要素。

**效果**：CoreML 60 篇 **505.6s → 85.9s（6.3×，1.43s/篇）**；内存不增（那"一份会话"本来就在
进程里，只是没被扔掉）。

**顺带解释了第 3 条**：CoreML 的编译**全局串行**（共享的 ane/XPC 服务），
所以"4 个进程各编译一次"= 排 4 次队，实测墙钟正好 4×。**缓存能救、并行不能救**，
因为缓存是"一台机床、一套字模、一批接一批印"，并行是"4 个人排同一台机床"。

### 2.2 复杂路径不再生成 N 个子答案

**问题**：`fanoutNode` 给每个子问题跑 `Loop.Run()`，而 `Run` 结尾**无条件**写答案。
`OnAnswerDelta = nil` 只是关掉**流式**，没关掉**生成**。于是复杂路径 =
**N 个子答案 + 1 次合成**，而子答案的唯一去处是合成 prompt 里的一行文字。

**代价**：本机生成恒定 ~6.4 tok/s，一次几百 token 的答案约 **1 分钟**。
3 个子问题 = 约 **3 分钟的纯浪费**（还不算每次的 prefill）。

**改法**：`Run` 拆成 `RunRetrieval`（检索 + 每轮 SCA，**不写任何文本**）与 `writeAnswer`；
`fanoutNode` 改用前者。现在复杂路径的模型调用只剩
decompose(1) + rewrite(0..R/子问题) + synthesize(1)。

**测试**：新增断言——复杂路径的"答案写入器"调用次数必须为 **0**、合成器恰好 **1**；
简单路径反之（1 和 0）。旧测试脚本里给"子循环答案"留的回复槽因此失效而**失败**，
这本身就是改动生效的证据。

## 3. 无效：并发类尝试

### 3.1 生成速度本身：7 个旋钮全部无差别

同一 200-token 请求，每个配置两轮：

| 变量 | 取值 | 稳态 tok/s |
| :--- | :--- | :--- |
| `num_thread` | 1 / 4 / 8 / 10 | 6.4–7.0 |
| `num_batch` | 512 / 1024 | 6.4–8.5 |
| `num_ctx` | 2048 / 4096 / 8192 | 6.4–8.4 |
| `num_gpu` | 0（纯 CPU）/ 99（Metal） | **8.2 / 7.3** ← CPU 略快 |
| `OLLAMA_FLASH_ATTENTION` | 0 / 1 | 6.5–7.5 |
| `OLLAMA_KV_CACHE_TYPE` | q8_0 / f16 | 6.4–8.5 |
| 常驻内存 | 全套应用常驻 / **整栈停掉** | 6.4–8.0 |

**结论**：**~6.4 tok/s 是本机环境的固定值**，7 个变量 + 两条后端（Metal 与 4 线程 CPU 一样慢）都动不了。
prefill 也只有 226 tok/s。首字延迟 0.08–0.18s（前缀缓存命中），所以**不是 SSE/传输层问题**。

**唯一能动的杠杆是 token 数量**：`PromptCharBudget(8192)` = 20,736 字符 ≈ 6,900 token ≈ 首字前 ~30s 的 prefill，
以及每轮各自的 prefill+生成。

### 3.2 生成并发（Ollama）

| 配置 | 2 次串行 | 2 次并发 | 加速比 |
| :--- | ---: | ---: | ---: |
| 默认（`NUM_PARALLEL=1`） | 3.7s | 4.2s | **0.87×** |
| `OLLAMA_NUM_PARALLEL=2` | 3.6s | 4.4s | **0.82×** |

**机制**：默认只有 1 个推理槽，第二个请求排队；开成 2 槽后两个请求争同一条内存总线，
KV cache 还被分成两半。两个都是负收益。

### 3.3 解析（版面检测）多进程

**CoreML 后端**（4 篇 PDF 旁路缓存）：

| 并发 | 总墙钟 | 每篇 |
| ---: | ---: | ---: |
| 1 | 8s | 8.0s |
| 2 | 17s | 8.5s |
| 4 | 32s | 8.0s |

**加速比 1.0×**：4 路墙钟正好等于串行 4×8s。原因见 §2.1——CoreML 编译全局串行。
代价实打实：每进程峰值 **836MB**，4 路要 3.3GB，而本机 swap 已用 11.3/12.3GB。

**纯 CPU 后端**（2 页/篇，6 篇）：

| 并发 | 每篇 | 相对串行 |
| ---: | ---: | :--- |
| 2 | 10.5s | **慢 1.75×** |
| 4 | 11.8s | **慢 2.0×** |
| 6 | 10.2s | **慢 1.7×** |

**比串行还慢**。这条与"加线程"的签名一致，指向同一机制（见 §5）。

### 3.4 解析多线程（intra-op）

同一页、同一输入，1/2/3/4 线程 = **1.9 / 3.7 / 5.4 / 7.4 s/页**。
**单调变慢**，而且不额外吃内存——这是"内存带宽受限"的教科书签名：
这个模型的算子是访存型，加线程只是让同一条总线更挤。所以默认固定
`DEFAULT_CPU_THREADS = 1`。

### 3.5 Laya 判定：线程池

sidecar 改双通道有界池（`decide` 并行、`parse` 串行）后实测：

| 配置 | 总墙钟（16 次判定） |
| :--- | ---: |
| 1 worker（对照） | **7.1s** |
| 2 workers | 7.5s |
| 4 workers | 7.6s |

**无加速**。把 state 拉大 4 倍（每调计算量 ×5）后仍然没有：4 次调用 1 worker 8.6s / 2 workers 9.9s
——所以**不是"每调固定开销主导"**。

### 3.6 Laya 判定：多进程（判别实验）

为了排除"同一进程内 ONNX 共享一个 intra-op 线程池导致串行"这一解释，做了这个实验：

| 配置 | 结果 |
| :--- | ---: |
| 单进程 16 次 / 1 worker | **7.1s** |
| 两个独立进程，各 8 次 / 1 worker | 每个 12.4s，总墙钟 **13s** |

两个进程**比单进程还差**。所以瓶颈**不在进程内的线程池**，而在整机共享的资源上，
且每进程多一份 1.2GB 权重让情况更糟。

### 3.7 Laya 判定：批量打分（尝试过并否掉）

**假设**：模型 fp32 1.2GB，每趟前向都要流一遍权重，那么一次前向覆盖多行就能摊薄。

**先验条件成立**：ONNX 图的 batch 维是动态的（`input_ids ['batch','seq']`、
`marker_pos ['batch','options']`、`qtype ['batch']`），所以批量在工程上可做。

**实测**（带标注数据，交替测量，各取最快；`rows=1` 是同一段代码跑两遍 → **噪声地板 0.97×**）：

| 行数 | 逐条 | 批量一次 | 加速比 | 选择一致 | max Δprob |
| ---: | ---: | ---: | ---: | :--- | ---: |
| 1 | 0.27s | 0.28s | 0.97× | ✓ | 0.0000 |
| 2 | 0.68s | 0.81s | 0.84× | ✓ | 0.0000 |
| 4 | 1.43s | 2.21s | 0.65× | ✓ | 0.0000 |
| 8 | 2.66s | 4.72s | **0.56×** | ✓ | 0.0000 |

复跑一次完全复现（0.58× / 0.56×）。

**数值上完全正确**：所有行填充到最长序列、填充被 attention mask 屏蔽，
8 行批量的选择与逐条**逐条相同、概率差 0.0000**——"填充对模型不可见"是被证明的，不是假设的。

**但性能是负的**，而且**成本是按 token 计的**：

- 逐条：2,202 token → 2.66s → **1.21 ms/token**
- 批量：同样的行 → 4.72s（填充后约 2,320 token）→ **2.03 ms/token（贵 1.7 倍）**

**没有东西可摊薄**：每行填充到最长宽度、attention 对宽度平方、批量的激活更大。
所以批量比逐条还慢，且随 batch 增大而更慢。

> 代码里 `LayaDecider.decide_many` 保留（`decide` 经由它，且组装/打分只有一份实现），
> 但 docstring 明确写着**实测更慢、不许当优化接上去**，并附上这张表。

## 4. 并发该用在哪（有效位置）

**判据是"这段工作在等 I/O，还是占资源"。** 本机实测：

| 阶段 | 耗时 | 性质 | 该并发吗 |
| :--- | :--- | :--- | :--- |
| 解析（版面检测） | 8.99s/篇（CPU，未缓存）→ **1.43s/篇**（CoreML + 会话缓存） | 访存/带宽受限 | ❌ 并发更慢（§3.3/§3.4） |
| Laya 判定 | 0.3–15s/次（随 state 长度） | 按 token 计的资源受限 | ❌ 并发无效（§3.5–3.7） |
| **嵌入（SiliconFlow HTTP）** | **0.2–1.05s/次**（3 次实测） | **纯网络等待** | ✅ **该并发** |
| upsert（qdrant） | ~0.05s | 网络 I/O | ✅ 该并发（但太小） |
| 生成（Ollama） | ~6.4 tok/s | 单槽排队 | ⚠️ 只有"少生成"有效 |

**已实现**：索引作业改为**异步 + 有界池**（`index_batch` 立即返回 job id、逐篇 `progress`、
`index_cancel` 可中断），额度 `indexBudget{Parse: 1, Write: 4}`——解析闸门只包住 `parse` 调用，
于是**文档 N 的嵌入/入库与文档 N+1 的解析可以重叠**。这才是 Go 并发在这里的正当用法。

> **诚实标注**：这条设计的**端到端收益尚未测量**。嵌入的延迟（0.2–1.05s/次）是实测的，
> "重叠能省下这部分等待"是推理。要落地结论需要一次带 `--no-cache` 的批量索引计时（做法见 §7.6，工具见 §9）。

另一个已确认的并发**正确性**前提（不是提速，但必须）：

- `sidecar.Client.Call` 写请求时**原本没有加锁**。macOS 的 `PIPE_BUF` 只有 **512 字节**，
  一个带 10k 字符 state 的 `decide` 请求远超它，写会被拆成多次 `write(2)`，
  两个并发 Call 就能**交错写入**，sidecar 收到坏行后回一个**与真实原因无关**的 parse error。
  已加独立 `writeMu`（不能复用 `c.mu`，否则写阻塞在满管道上会与读者互等）。
  用**变异测试**验证过：去掉锁后测试精确报出交错损坏。
- 同一会话被多个线程共享是**验过的**：4 线程并发 `decide` 无异常、答案一致
  （onnxruntime `Run` 线程安全这个假设不再只是文档上的一句话）。

## 5. 机制归纳：为什么都没提速

四条独立路径（解析多进程 1.0×、解析多线程单调变慢、Laya 多进程更差、Laya 批量 0.56×）
指向同一个结论：

> **这台机器上是一个已饱和的共享资源在限制，而不是核数。** 叠加在它之上的是
> **按 token 计算**的单趟成本。

具体表现：

- 加线程不额外吃内存却变慢 → 总线/带宽饱和；
- 加进程更慢 → 每进程多一份权重，进一步压总线与内存；
- 批量更慢 → 每 token 的成本不降反升（填充 + 二次方 attention）；
- **`num_gpu=0`（纯 CPU）比 Metal 还略快** → 连 GPU 路径也不是瓶颈所在。

**我无法从这些数据里分离的一点**：按 token 的成本中，"算子计算"与"访存流量"各占多少。
要 profiler 才能定。但**两者都推出同一个结论**——批量与并发都无效。

## 6. 参照：RAGFlow 的做法（它为什么能靠并发提速）

本机有一份 RAGFlow 的 Go 实现（`/Users/cbn/workspace/RAGFlow`），它的并发是**显式、有限、分阶段**的：

| 机制 | 位置 | 默认值 |
| :--- | :--- | :--- |
| 跨文档 worker 池 | `internal/ingestion/service/ingestion_service.go:628`（`startWorkerPool`） | `max_concurrent_workers = 2`（默认在 `internal/server/config/ingestor_config.go:35`、`conf/service_conf.yaml:100`） |
| 单文档按页并行 | `internal/deepdoc/parser/pdf/parser_concurrency.go:115` | `min(runtime.GOMAXPROCS(0), DeepDocConcurrency())` |
| **推理预算（信号量）** | `internal/deepdoc/native/inference_limit.go:33`（`slots chan struct{}`） | `deepdoc.inference_concurrency = 4`（默认见 `internal/server/config/deepdoc_config.go:33`） |
| 会话池 + 权重共享 | `internal/deepdoc/native/session_pool.go`、`session.go` 的 `weightCache` | 建一次、反复借还 |
| **intra-op 线程数** | `internal/deepdoc/native/session.go:36` | `intraOpThreads = 1`（**硬编码**） |
| 后端 | `internal/deepdoc/native/session.go:9` | **纯 CPU（by design）**；已核对：全仓无 `CoreML/CUDA/TensorRT/Dml` ExecutionProvider |
| OCR 批量 | `internal/deepdoc/parser/pdf/parser_ocr.go:25` | `recBatchNum = 16`（最多 16 行拼一次 Run） |

> 上表的行号已逐条 `sed` 核对过（引用错的行号比不引用更糟）。

**它为什么有效**：每会话只开 1 个 intra-op 线程 → 一次 Run 约吃 1 个核 → 4 个会话正好铺满 4 个核，
**并行度直接换成吞吐**。另外它把 OCR 的**最多 16 行拼成一次 Run**（`parser_ocr.go:25`）——
但那一条在我们这里是**反的**（§3.7），原因就是 §5 的"按 token 计的成本"。

**结论**：RAGFlow 的成功前提（CPU 算子可跨核摊开、无全局串行的编译步骤）在这台 Mac 上**不成立**。
照抄它的并发结构不会有收益，但它的**预算化思想**值得保留：
并发上限应该是一个**显式可配的数**，而不是"池子有多大就开多大"。

## 7. 未来可尝试的方向

按"打在哪、怎么验收"组织。**优先级从上到下**。

### 7.1 量化 Laya（int8）——最高优先

- **打在哪**：成本按 token 计、每 token 都要搬权重，而部署包给的是 **fp32（1.2GB）**，从未量化过。
  int8 能把访存砍到约 1/4，计算也可能受益。这是**唯一一条没试过、且直接打在真正瓶颈上**的路径。
- **怎么验收**：`scripts/eval_laya.py --bucket 400 --per-class 8`。当前基线
  **准确率 0.938（正例 1.000 / 负例 0.875）**，官方门槛是**域内宏平均 ≥85%**。
  量化后跑同一命令即可判断掉不掉分；顺带用 `scripts/bench_laya_batch.py` 量速度。
- **风险**：可能掉分；掉分就按官方建议"加数据 / 多训 1 epoch"，而不是硬上。

### 7.2 少判几次、判窄一点（策略旋钮，已有）

- `DefaultMaxStateChars = 10000`（≈2.3k token，填满约 15s/次）；`SCAMaxRounds`（Medium=3）；
  `ActionMaxTurns = 12`；复杂路径改成"每子问题各自 kbinfo"后，判定的 state 比并集小得多。
- **为什么这是有效杠杆**：既然按 token 计费，**减少 token 总量是直接的**。
  实测准确率在整个长度区间没有提升（370 tok 93.8%、2k tok 91.7%、8k tok 4/4，正例全程 100%），
  所以压 short 是"免费"的。

### 7.3 让生成更快：只有"少生成"

- 7 个旋钮全平（§3.1），所以**换更小的模型**或**更少的 token**是仅有的两条。
- 前缀缓存已经用上（`Loop.Warm` 预热 tool-plan 前缀，首字 0.08–0.18s）；
  `PromptCharBudget` 是 prompt 侧护栏。
- 值得试：把 Laya 已经能判的事情**别再让生成模型重复判**（当前结构已朝这个方向）。

### 7.4 给 Laya 上加速器（中级）

- 现在 `DEFAULT_PROVIDER_CHOICE = "cpu"`。但**先按 §2.1 的教训设计实验**：
  CoreML 的编译是全局串行的，只有在**会话缓存生效**之后才可能划算。
  Laya 的会话已经是进程级缓存 ✓，所以现在试 CoreML 的**前提已经具备**（当时布局模型不具备）。
- **验收**：`scripts/eval_laya.py` 对拍（两种 provider 的判定必须逐条一致）+ 计时。

### 7.5 解析提速：改输入而不是改并发

- 降 DPI / 降输入分辨率（直接砍 ANE/CPU 的工作量）；
- 换更小的版面模型；
- 已生效的最大一项仍然是**会话缓存**（6.3×），以及解析结果缓存（命中 0.07s vs 冷跑 8.43s）。

### 7.6 把"阶段重叠"量出来（廉价，且可能有收益）

- 设计已存在（`indexBudget{Parse:1, Write:4}`：解析串行、嵌入/入库并发重叠）。
- **待测**：一次带 `--no-cache` 的 100 篇批量索引，对比 `Write` 额度 1 与 4 的总墙钟。
  这是目前唯一"并发真的应该有用"的地方，**应该先证明再优化**。

### 7.7 不要重试的路（记录以免重复劳动）

- 解析多进程/多线程（§3.3、§3.4）；
- Laya 判定线程池 / 多进程 / 批量（§3.5–3.7）；
- Ollama 并发或 `NUM_PARALLEL`（§3.2）；
- 生成侧的 7 个旋钮（§3.1）；
- 指望 GPU/Metal 救场（`num_gpu=0` 反而略快）。

**结论先行**：

| 11 | **REFRAG 式选择性证据压缩**（受控 A/B） | ✅ **TTFT 25.8s → 6.4s（4.01×）**，整次调用 80.6s → 46.1s，答案长度不变 | 只把 top-K 段落展开成原文，其余进入解码器的是"摘要"，**提示词 token 少了 1.95×** |

### 10.1 REFRAG 是什么，以及哪一部分搬得过来

论文的三个动词是 **compress · sense · expand**：检索到的段落不再以 token 形式进解码器，
而是先被一个轻量编码器压成**一个 chunk embedding**，再由一个 RL 策略决定**哪几段值得展开回原文**。
报告的是 k=16 时 **16.53× TTFT**（带缓存）、k=32 时 **32.99×**，且困惑度无损。

**搬得过来 / 搬不过来的，逐条记下**（"听起来像白拿"的那条最容易搞错）：

| REFRAG 的部件 | 在 freerag 里 | 为什么 |
| :--- | :--- | :--- |
| compress：chunk → 一个 embedding | ✅ 改写成**文本摘要（gist）**：段落首部的完整句子，末尾标 `[…]` | 真做需要**继续预训练**一种 encoder–projection 把 embedding 对齐到解码器的 token 空间。freerag 跑的是**冻结的 Qwen3-4B GGUF**（Ollama），没有任何训练路径；对未训练的解码器，唯一能读的"压缩表示"就是文本本身 |
| sense：RL 策略决定展开谁 | ⚠️ 用**检索排名**近似：top-`ExpandTop` 段展开，其余压缩 | 同样无法训练策略。这是一个**启发式顶着策略的位置**，所以代码里就叫启发式，不叫策略 |
| expand：被选中的段以原文进入 | ✅ 完全相同：位置、编号 `[n]`、header 都不变 | 提示词仍是**一条扁平的自回归序列**，引用标记仍然解析得到 |
| **reuse：chunk 表示可预计算** | ❌ **不搬，也没假装搬** | 它的 embedding 要一次编码器前向，所以预计算值钱；我们的 gist 是一次**切片**，没有东西可摊薄。这条被写进 `refrag.go` 的注释，因为"REFRAG 会预计算"听起来像免费的收益 |
| 系统性质：prefill 随 **chunk 数**而非 **token 数**增长 | ✅ 这正是 §10.2 量到的比值 | 池越深收益越大 |

**质量代价是诚实的**：gist 会**丢 token**（embedding 是编码而不是丢）。论文能说"困惑度无损"是因为解码器
被训练过；这里没有。所以：① 被压缩的段落**必须在 header 里明说**（`| compressed`），否则模型会
把半段当整段读；② 压缩比是**配置出来的**（`ExpandTop`），**不是**一个可以声称无损的常数。

### 10.2 受控测量：同一问题、同一证据池，只换提示词

端到端跑 `ask` 量不出这件事：一次问答 90–300s，其中检索、改写、SCA 轮数占大头，而提示词只影响
**写答案那一次调用**。所以先在能控住变量的地方量它——
`internal/agent/refrag_live_test.go`：同一个问题、同一个证据池（eval 语料的真实 chunk）、同一个生成器，
只换证据块的渲染方式；模型**先预热再计时**，两臂**交替跑两遍取最快**（本机噪声下限约 ±20%，见 §1.1）。

```
$ FREERAG_LIVE_OLLAMA=1 go test ./internal/agent -run TestRefragLiveTTFT -v

pass 1 full    evidence  13468 chars  TTFT  38.07s  total  90.86s  answer  908 chars
pass 1 refrag  evidence   6818 chars  TTFT   6.44s  total  46.09s  answer  949 chars
pass 2 full    evidence  13468 chars  TTFT  25.83s  total  80.56s  answer  961 chars
pass 2 refrag  evidence   6818 chars  TTFT   8.45s  total  50.59s  answer  887 chars
best-of-2: full TTFT 25.83s -> refrag TTFT 6.44s (-19.39s, 4.01x); total 80.56s -> 46.09s
```

**读法（三点，第三点容易被漏掉）**：

1. **TTFT 4.01×**，节省的 19.4s 就是被删掉的那 6650 字符的 prefill（≈2200 token @ 226 tok/s ≈ 10s，
   加上 TTIT 随上下文变长的部分）。与论文的 k 不是一回事——它是**按比例**省，我们按**丢失的 token 数**省，
   数值接近不代表机制相同。
2. **整次调用也快了 34.5s**，而两臂的答案长度相当（908/961 vs 949/887 字符）。这不是靠"答短一点"换的：
   提示词短了，**TTIT 也随之下降**（论文的第二条宣称），预热 + 交替测量已经把模型加载和提示词缓存排除在外。
3. **答案长度没变**是本测量里最重要的守卫。压缩最容易的作弊方式是让答案变短，那样 TTFT 必然下降——
   和 plan.md §13.2 里"不许拿拒答换分"是同一类问题。

**离线部分（确定性，不需要模型）**，同一份 `refrag_live_test.go` 在 731 个真实 chunk 上量：

```
pool  6:   9523 chars ->   6225 chars (1.52x),  4 expanded /  2 compressed     6/6 段保留 → 6/6
pool 10:  13468 chars ->   6818 chars (1.95x),  6 expanded /  4 compressed    10/10 段保留 → 10/10
pool 20:  19830 chars ->   9108 chars (3.50x),  7 expanded / 13 compressed    14/20 段保留 → 20/20
```

**第三列是"上下文扩展"那一面**：池 20 时未压缩的块已被 `MaxPromptChars(20736)` 截断，
20 段里只有 14 段进得去；压缩后 **20 段全都在**。所以压缩的真实收益是
**同一份预算下既装得下更多段落、又用掉更少 token**，比值只是它的一半。

**默认关闭**（`FREERAG_REFRAG` 未设即关）。理由与 §1.1 第 4 条同源：**没有实测过的提示词改动，
和回归无法区分**。关闭时提示词与改造前**逐字节相同**（`TestRefragDisabledRendersTheUncompressedPrompt` 锁死），
所以基线是一个不动的点。

### 10.3 端到端 A/B（真实 `ask`）

受控测量回答"机制是否成立"，端到端回答"系统里还剩多少"。同一批问题、同一 KB、
**逐题交替**两臂（第 2 遍反序）、生成器**先探测**（§13.27 的纪律）：
`scripts/measure_refrag.py`。

**先加了一个仪器，因为没有它这个 A/B 读不出来。** 端到端唯一能归因到提示词的数是
**写答案那一次调用**，而"这次调用花了多久"混着两件事：prefill（提示词决定）与生成（答案长度决定）。
于是 `OllamaModel` 开始把生成器自己报的 `prompt_eval_count / prompt_eval_duration /
eval_count / eval_duration` 带进 `Reply.Usage`，两条路径各写一行 trace：

```
[Usage] prompt 6480 tok in 21.3s (304 tok/s), output 214 tok in 32.4s (6.6 tok/s).
```

这不是为这次测量临时加的表——`docs/plan.md §13.1` 的适应度函数里 `成本 = 端到端墙钟 + 生成 token`，
而**"生成 token"这一半此前根本没人报过**，所以一次改动可以拿延时换质量（或反过来）而不被看见。
带 `Usage` 的一个副作用值得记：Ollama 在**每个 chunk 上重复累计值**，
把它们相加会得到"token 数 = 真实值 × chunk 数"——一个看起来完全正常的错数。测试里因此
专门喂了重复的累计值（`TestCompleteStreamCapturesGeneratorUsage`）。

**第一次尝试被作废，理由记在这里**：初版两臂是**整块**跑的（3 题 full、再 3 题 refrag），
于是①机器漂移（热、后台负载）被算进臂差；②更要命的是**循环本身不可复现**——
同一道题两臂拿到的证据池规模不同（35 段 vs 25 段），因为改写、工具选择、fan-out 合并
每一步都是决策，合并池是它们的并集。**两臂的池不同，任何延时差就不是提示词差。**
v1 的产物留在 `eval/runs/refrag-e2e-blockorder-abandoned.jsonl`，只作为"为什么块设计不能用"的证据。
v2 改成**逐题交替**，并把**同臂重复**当作可复现性对照一并报告——
如果同臂两次的池都在飘，那就是这次 A/B 的分辨率上限。

**实测（2 题 × 2 遍 × 2 臂 = 8 次 `ask`，`eval/runs/refrag-e2e.jsonl`）**：

| 臂 | 题 | 遍 | 池 | **进入提示词** | 源字符 | 提示词 token | prefill | prefill ms/tok | 输出 token |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| full | q0027 | 1 | 35 | **9 / 35** | 24,311 | 4638 | 0.05s | 0.01 | 95 |
| refrag | q0027 | 1 | 35 | **33 / 35** | 71,644 | 5091 | 30.27s | 5.95 | 205 |
| full | q0076 | 1 | 26 | **10 / 26** | 22,804 | 5210 | 25.59s | 4.91 | 373 |
| refrag | q0076 | 1 | 26 | **26 / 26** | 47,052 | 5024 | 18.75s | 3.73 | 261 |
| refrag | q0027 | 2 | 35 | 33 / 35 | 71,644 | 5091 | **0.04s** | 0.01 | 259 |
| full | q0027 | 2 | 35 | 9 / 35 | 24,311 | 4638 | 24.20s | 5.22 | 154 |
| refrag | q0076 | 2 | 26 | 26 / 26 | 47,052 | 5024 | **0.05s** | 0.01 | 331 |

> ⚠️ **这张表是在 temperature 修复之前跑的**（见结论 1），所以池只在**同一场之内**
> 才对得上；跨场次会跳到另一个分支。表里的数字本身仍然有效（同一场、逐题交替），
> 但"两臂池相同"这件事是**这一场**的性质，不是系统的保证。修复后重跑的
> `eval/runs/refrag-stream.jsonl` 才是可复现的那一份。

**四条结论，第二条推翻了我原本的预期。**

1. **可复现性本身出了问题，根因是 `temperature=0` 从未生效——已修。**
   在 v2 这一场里同一题两臂拿到**同一个池**（q0027 都是 35 段，q0076 都是 26 段），
   同臂两遍的源字符数逐字节相同。但**跨场次不成立**：同一题、同一臂，在另一场里是
   **44,218** 字符（池 25），而这一场是 **71,644**（池 35）。
   追下去是 `OllamaModel` 的一个语义 bug：

   ```go
   if m.Temperature > 0 { options["temperature"] = m.Temperature }   // 0 被吃掉了
   ```

   `FREERAG_GENERATION_TEMPERATURE=0` —— **每一条测量纪律都写着要设的那个值** ——
   因此从来没有发到服务端，实际采样温度是 Ollama 的默认 **0.8**。
   改写出来的查询于是每次不同，池就在两个分支之间跳（44k / 72k）。
   这与 §13.17 记的"温度 0 把带宽从 0.0793 降到 0.0271"**矛盾**：那个下降另有来源
   （或者本身就是噪声）——**旧结论需要按这条重新审视**，本文不替它辩护。

   修法是把"未设"与"设成 0"分开：`Temperature < 0` 才表示"用服务端默认"，`0` 就是贪心。
   修完立刻复测（同题、同臂、两遍，`eval/runs/refrag-stream.jsonl`）：
   **四个样本的池、提示词 token、答案长度（1259 字符 / 228 token）逐字节相同**，
   只剩时间戳在动。**这才让下面几条成立。**

   > 教训与 §13.15、§13.27 同类，但这次错在**开关**上：一个"设了但没接上"的旋钮，
   > 比没有这个旋钮更坏——它让所有跑在这个"受控"配置下的对比**看起来**受控。
   > §13.17 已经写过"旋钮必须先证明是活的才能被扫"，那条讲的是**死代码**；
   > 这一条讲的是**值在到达边界前被吞掉**。

2. **在固定预算下，压缩买到的是覆盖，不是速度。** 预算 `MaxPromptChars(20736)` 是那个真正的闸门：
   - 未压缩：35 段里只有 **9 段**进得去（10/26）；
   - 压缩后：**33 段**进得去（26/26），即提示词里带着 **71,644 字符**的源证据 vs 24,311 —— **2.9×**。

   而两臂的**提示词 token 几乎相同**（4638 vs 5091；5210 vs 5024）。
   这是必然的：块本来就填不满预算的人会去填满，**把预算花完**，于是照旧塞满。
   **所以端到端没有 prefill 的节省可以声称**；速度收益来自"同覆盖"（§10.2 的 4.01×）
   或者"把预算调小"。**REFRAG 在这里换到的是"同一个窗口里多装 3 倍证据"**——那是它的另一半价值
   （论文里叫 context extension），而这一半在固定预算下才是端到端的可见收益。

3. **prefill 的实测被 Ollama 的提示词前缀缓存支配，因此端到端不能拿它做臂间统计。**
   未命中缓存的样本是 **3.7–6.0 ms/token**（≈170–270 tok/s）；而**命中缓存的样本是 0.01 ms/token**
   （5000 token 用掉 0.04s）。表里两个 `0.04s / 0.05s` 就是**第 2 遍命中了第 1 遍留下的缓存**——
   同一提示词第二次出现是免费的。
   **这条要写进纪律**：在这套系统上做 A/B，**同一提示词的第二次重复测的是提示词缓存，不是提示词**。
   它和第 §13.15 的截断伪影是同一类错误——**测量工具的默认行为被当成了系统性质**。
   要量 prefill 就必须让每次都是冷提示词（换题、或让前缀不同），或者干脆看 **ms/token** 这个不变量。

4. **答案长度在两臂之间不可控**（输出 token 95 vs 205，373 vs 261）：压缩后模型看到更多证据，
   自然写得更长。所以 **`[Synthesize] written in` 不能直接对比**——它混着 prefill 与输出长度。
   这正是 §10.3 开头加 `Usage` 的原因，而 `Usage` 一进来就把上面三条全部暴露出来了。

**端到端判据（一句话）**：在**固定预算**下 REFRAG **不改变延迟**（提示词 token 持平），
它改变的是**同样的窗口里能装多少证据**（9→33 段，源字符 2.9×）；
**速度收益需要固定覆盖才有**——那正是 §10.2 的受控测量，**TTFT 4.01×**。
两者不矛盾，它们是同一个预算下不可能同时拿到的两个东西。

### 10.4 流式帧合并：一个**结构上不可能**帮上忙的方案

**要解决的问题是真的**：答案逐 token 推送，每个 token 一条 JSON-RPC 通知，
所以 900 字符的答案 ≈ **165 条帧**（实测），每帧一次 JSON 编码 + `write(2)` + readline + `json.parse` + 一次 IPC 跳转。
服务端把 SSE 流合批是标准做法。

**但在这里它不可能变快**，原因是 §3.1 已经量过的那个常数：

- 生成 **~6.4 tok/s** ⇒ 帧与帧之间隔 **~156 ms**，而一帧的成本是**微秒级**。**没有东西可摊薄。**
- 合批窗口是**纯加的延迟**：窗口 120ms 时，每个 token 至多晚 120ms 到达，而省下的是微秒。
- 于是实现里写死了一条纪律：**首帧立即发出、永不等待**（TTFT 是不能动的那个数），
  其余按窗口合并。这是"不伤害"的设计，不是"更快"的设计。

因此 `FREERAG_STREAM_COALESCE_MS` **默认 0（关闭）**，并在 `internal/ipc/coalescer.go` 里写明了
它的适用条件：**当生成端比窗口快一个数量级时**（换 GPU / 更小的模型 / 更快的后端），帧成本不再免费，
同一套合批才是收益。代码留着，因为"试过并写出条件"比"没试过"有用。

**实测（temperature 修复之后，同题 × 2 臂 × 2 遍 = 4 次 `ask`，`eval/runs/refrag-stream.jsonl`）**：

| 臂 | 遍 | 分片 | **帧** | TTFT | 总时长 | 答案 | 输出 token | 输出耗时 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| refrag | 1 | 227 | **227** | 113.3s | 163.6s | 1259 | 228 | 50.25s |
| refrag+stream | 1 | 227 | **214** | 118.0s | 167.6s | 1259 | 228 | 49.63s |
| refrag+stream | 2 | 227 | **214** | 114.1s | 160.2s | 1259 | 228 | 46.07s |
| refrag | 2 | 227 | **227** | 114.0s | 162.1s | 1259 | 228 | 48.08s |

`[Stream] 227 fragment(s) -> 214 frame(s) (window=120ms).`

**读法**：

- **帧数 −5.7%（227 → 214）**。窗口 120ms 而分片间隔约 **220ms**（50s / 227 帧），
  所以绝大多数分片**等不到下一个同伴**，只能自己成帧。合并掉的 13 帧是 Ollama 偶尔一次吐多个 token 的地方。
- **延迟没有差别，也按设计不该有差别**：首帧从不等待，其余分片的额外延迟被窗口上界约束，
  而省下的是**微秒级的编码 + write + parse**。
- 因此这一条的结论是**"不伤害"而不是"更快"**——它证明了这个方案在这里无收益，
  也给出了它的适用条件。**把它接上去的唯一理由是把帧数本身当成成本**（例如客户端是慢的移动端渲染）。

**同一次运行还顺带给出了 prefill 的另一个伪影**：`[Usage] prompt 5091 tok in 40–50ms
(≈110,000 tok/s)` —— 四个样本的提示词**完全相同**，所以全部命中前缀缓存，
这个"prefill"是缓存命中价，不是 5091 token 的真实成本。同批样本里冷提示词的实测是
**3.7–6.0 ms/token（≈170–270 tok/s）**。**报告 prefill 时必须说清楚是冷还是热。**

### 10.5 不要重试的路（记录以免重复劳动）

- **在提示词层面复现 REFRAG 的 encoder**：做不到。解码器没被训练过读 chunk embedding，
  硬喂投影向量只会得到胡话。要真做，前提是一次**继续预训练**（CPT + 重建任务 + 课程学习），
  那不是本机的算力能碰的。
- **把 gist 预计算到索引里**：gist 是切片，省不下东西。REFRAG 的"预计算"优势**不成立**。
- **指望合批降低流式延迟**：见 §10.4，结构上不行。真正降 TTFT 的是**少 prefill**。

### 10.6 新增的旋钮

| 环境变量 | 默认 | 说明 |
| :--- | :--- | :--- |
| `FREERAG_REFRAG` | 空（**关闭**） | `1/on/true/yes` 打开选择性压缩；其余取值一律关闭 |
| `FREERAG_REFRAG_EXPAND_TOP` | `4` | 展开排在最前的几段；其余进 gist |
| `FREERAG_REFRAG_GIST_CHARS` | `240` | 每段保留多少字符（小于 40 视为配置错误，回落到默认） |
| `FREERAG_STREAM_COALESCE_MS` | `0`（**关闭**） | 答案分片合并窗口 |
| `FREERAG_STREAM_COALESCE_RUNES` | `0`（仅窗口决定） | 合并帧的字符上限，到顶即发 |
| `FREERAG_GENERATION_TEMPERATURE` | `0.2` | **`0` 就是贪心**（现在会真的下发）；负值才表示"用服务端默认" |

`ask` 的结果多出一个 `prompt_stats`（`evidence_chars` / `evidence_chars_raw` / `expanded` /
`compressed` / `usage`），并在确实发生压缩时往 trace 里写一行
`[Refrag] evidence N chars -> M chars (x.xx×) …`；每次实际调用另有一行
`[Usage] prompt P tok in … , output O tok in …`。**压缩那一行在关闭时不出现**——
一条每次都打印 `1.00x` 的日志会把唯一有用的那行训练成噪声。`usage` 则每次都报，
因为一次调用的**成本**在"没压缩"的运行里同样是个事实。

### 10.7 顺带修掉的两处（都让验收从红变绿，也都值得记）

`scripts/acceptance.sh` 这一轮是 **12/12**，但把它跑绿的两次修改都不是"为了让测试通过"：

1. **复杂路径的 `rounds` 一直是 0。** `synthesizeNode` 构造 `Result` 时没有填 `Rounds`，
   而简单路径有；`assert_flow.py` 检查 `rounds >= 1`，于是**任何走复杂路径的验收都报
   "ask ran no round"**——一个关于检索的失败信息，实际是字段没填。
   已改为填**最深的那个子问题**的轮数（子循环是并发的，所以墙钟对应最慢的那个，
   "这次跑了几轮"没有别的答案）。
   **这条先被证明是既有的**：把本次改动 `git stash` 后重建、重跑同一条 `ask`，
   老二进制同样给出 `route=complex rounds=0`。不然就是我把验收弄坏了。
2. **验收脚本还在断言 `draft`。** 那个字段在"循环不再为判定写草稿、只写一次答案"时
   就改名成 `answer` 了；断言没跟着改，于是**每次运行都少一个通过项**。
   一个永远报一条失败的套件，会把人训练成忽略失败（README 的"12/12"因此也是旧的）。

## 11. Laya 会话预热（2026-10-06）

**起因**：一次 `ask` 的 154s 里，路由那一步占了 **19.9s**——而它只问 Laya 一个二选一。
逐步计时定位到：Laya 的 ONNX 会话是**首次决策时才构建**的（`sidecar/laya.py` 的
`LayaDecider._load`：fp32 检查点 ~1.7 GB，走 CPUExecutionProvider），而 `HasLaya` 只检查
文件是否存在，所以启动日志里的 "Laya: typed decisions wired" **不代表会话已就绪**。

**改动**：`cmd/freerag/main.go` 的 `warmDecider()`，与 `warmGenerator()` 并列、不等待、
失败只记日志。两者刻意并发：一个在 GPU 上装权重，一个在 CPU 上建会话，互不占对方的路。

**实测**（MacBook Air M5，同一问题、同一 KB，预热已完成 vs 未完成）：

```
未预热   [thinking] 0.4s → [Route] 19.9s → [Decompose] 103.0s（其中排队）→ 完成 154.2s
预热后   [thinking] 0.1s → [Route]  0.4s → [Decompose]   1.4s            → 完成  51.3s
启动日志：model warm-up done in 6.288s / Laya warm-up done in 15.975s
```

**读数纪律**：两次的分解/合成都被当时另一路 `ask` 占着 Ollama 的**单槽位**（`-np 1`）
污染过，所以只有路由这一项的对比是干净的——它走的不是 Ollama。整次 154s → 51s 里
有多少来自排队、多少来自预热，本测量不声称。

**剩下的一半没被动**：写答案那一次调用仍是 **37.2s / 272 字 / ~4.5 tok/s**。这是
§1.1 那条"唯一能动的杠杆是 token 数量"的另一半：预热搬走的是**固定开销**，
而 4.5 tok/s 是这台机器的解码墙（冷机首段实测 44.7 tok/s，数分钟后落到 4.5–7），
提示词再短也不会让它变快，只会让需要生成的 token 变少。
