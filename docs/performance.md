# 并行与加速：测量纪要

本文记录 freerag 在"提速"上做过的全部尝试——**做成了什么、没做成什么、为什么**。
写下来的目的不是总结成绩，而是让下一次有人想"要不并行一下"时，先看到已经试过什么、
以及每条路的**实测结论与机制**。

所有数字都是本机实测（除非明确标注"估算""推理"）。**结论先行**：

| # | 尝试 | 结果 | 一句话机制 |
| :-- | :--- | :--- | :--- |
| 1 | **解析会话缓存**（建一次 · 多篇复用） | ✅ **6.3×**（505.6s → 85.9s / 60 篇） | 构建步骤被塞进了每篇文档的热路径，是重复劳动 |
| 2 | **复杂路径不再生成 N 个子答案** | ✅ 省掉 N 次完整生成（每次约 1 分钟） | 那些子答案的唯一读者是合成 prompt，内容在合并池里已有 |
| 3 | 解析多进程并行 | ❌ **1.0×**（8.0/8.5/8.0s 每篇） | CoreML 编译全局串行，多进程只是排队 |
| 4 | 解析纯 CPU 多进程并行 | ❌ **1.7–2.0× 更慢** | 内存带宽饱和（加线程 = 更挤总线） |
| 5 | 解析多线程（intra-op） | ❌ 1/2/3/4 线程 = 1.9/3.7/5.4/7.4s **每页** | 同上：算子不并行，只增竞争 |
| 6 | **Laya 判定 · sidecar 线程池** | ❌ **无加速**（16 次：7.1/7.5/7.6s @ 1/2/4 worker） | 一个饱和的共享资源，不是核数 |
| 7 | Laya 判定 · 多进程 | ❌ **更差**（两进程 13s vs 单进程 7.1s） | 同上，且各自多占 1.2GB |
| 8 | Laya 判定 · **批量打分** | ❌ **0.56×（慢 1.8 倍）** | 成本按 token 计，不是按前向趟数计，没有东西可摊薄 |
| 9 | 生成（Ollama）并发 | ❌ 0.87×（默认）/ 0.82×（`NUM_PARALLEL=2`） | 单槽排队；开多槽后争同一条总线 |
| 10 | 生成速度本身（7 个旋钮） | ❌ 全部无差别，恒定 **~6.4 tok/s** | 本机环境的固定值，能动的只有 **token 数量** |

**主题一句话**：这台机器上，凡是"同时做更多事"的尝试都**无效或更差**；
真正提速的两次都是**"少做重复的事"**（建一次、别生成）。

## 1. 环境与方法

- **机器**：MacBook Air，M5，10 核（4P+6E），**16GB**，无风扇。
- **常驻**：VS Code + Electron + 内核 + sidecar + qdrant + Ollama（实测这些是否常驻对结果**无影响**，见 §3.1）。
- 复跑脚本见 §7。

### 1.1 四条方法论教训（都是踩过的坑）

1. **跨场次的数字不可比。** 同一份代码、同一份数据、同一批用例（带标注 400 桶），
   Laya 单次判定中位数在两次会话里是 **3.2s 与 0.4s**——差别只在于当时机器的负载
   （内存压力、谁在抢带宽）。**所以本文所有对比都取自同场次、交替测量**；引用跨场次数字时已注明。

2. **噪声下限约 ±20%。** 批量测量里 `rows=1` 那一行跑的是**同一段代码两遍**，
   它给出 0.97×——这就是这台机器的噪声地板。低于 1.2× 的"加速"不要相信。

3. **onnxruntime 的首次 `Run` 有一次性开销。** 同一条判定，首次 1.07s、之后 0.26s
   （执行计划懒构建）。不预热就计时，会得到"8 条逐条比 2 条还快"这种自相矛盾的结果——
   我的第一次批量测量就是这么错的。

4. **缓存会把"改进"变没。** 解析缓存命中时单篇 0.07s，冷跑 8.43s。
   任何"优化前后对比"都必须 `--no-cache`，否则测的是缓存。

## 2. 有效：真正提速的两处

两处的共同点：**都不是并发，而是删掉重复劳动**。

### 2.1 解析会话缓存（6.3×）

**问题**：`pipeline.make_detector()` 每篇文档新建一个 detector，而 `layout_onnx._load()`
只把 ONNX session 缓存在**实例**上。于是每解析一篇文档，就重新构建一次会话。

**代价有多大**（同一模型、两种后端）：

| 后端 | 建会话 | 每页推理 | 每篇（60 篇 / 234 页实测） |
| :--- | ---: | ---: | ---: |
| CoreML（657/681 节点编译给 ANE） | **6.90s** | 0.25–0.39s | 8.43s（其中 **82% 是建会话**） |
| 纯 CPU（1 线程） | **0.14s** | 1.9–2.27s | 8.99s |

**改法**：`session_for(path, providers, cpu_threads)` —— 进程级注册表 + 双重检查锁，
key 是决定"编译产物长什么样"的三要素。

**效果**：CoreML 60 篇 **505.6s → 85.9s（6.3×，1.43s/篇）**；内存不增（那"一份会话"本来就在
进程里，只是没被扔掉）。

**顺带解释了第 3 条**：CoreML 的编译**全局串行**（共享的 ane/XPC 服务），
所以"4 个进程各编译一次"= 排 4 次队，实测墙钟正好 4×。**缓存能救、并行不能救**，
因为缓存是"一台机床、一套字模、一批接一批印"，并行是"4 个人排同一台机床"。

### 2.2 复杂路径不再生成 N 个子答案

**问题**：`fanoutNode` 给每个子问题跑 `Loop.Run()`，而 `Run` 结尾**无条件**写答案。
`OnAnswerDelta = nil` 只是关掉**流式**，没关掉**生成**。于是复杂路径 =
**N 个子答案 + 1 次合成**，而子答案的唯一去处是合成 prompt 里的一行文字。

**代价**：本机生成恒定 ~6.4 tok/s，一次几百 token 的答案约 **1 分钟**。
3 个子问题 = 约 **3 分钟的纯浪费**（还不算每次的 prefill）。

**改法**：`Run` 拆成 `RunRetrieval`（检索 + 每轮 SCA，**不写任何文本**）与 `writeAnswer`；
`fanoutNode` 改用前者。现在复杂路径的模型调用只剩
decompose(1) + rewrite(0..R/子问题) + synthesize(1)。

**测试**：新增断言——复杂路径的"答案写入器"调用次数必须为 **0**、合成器恰好 **1**；
简单路径反之（1 和 0）。旧测试脚本里给"子循环答案"留的回复槽因此失效而**失败**，
这本身就是改动生效的证据。

## 3. 无效：并发类尝试

### 3.1 生成速度本身：7 个旋钮全部无差别

同一 200-token 请求，每个配置两轮：

| 变量 | 取值 | 稳态 tok/s |
| :--- | :--- | :--- |
| `num_thread` | 1 / 4 / 8 / 10 | 6.4–7.0 |
| `num_batch` | 512 / 1024 | 6.4–8.5 |
| `num_ctx` | 2048 / 4096 / 8192 | 6.4–8.4 |
| `num_gpu` | 0（纯 CPU）/ 99（Metal） | **8.2 / 7.3** ← CPU 略快 |
| `OLLAMA_FLASH_ATTENTION` | 0 / 1 | 6.5–7.5 |
| `OLLAMA_KV_CACHE_TYPE` | q8_0 / f16 | 6.4–8.5 |
| 常驻内存 | 全套应用常驻 / **整栈停掉** | 6.4–8.0 |

**结论**：**~6.4 tok/s 是本机环境的固定值**，7 个变量 + 两条后端（Metal 与 4 线程 CPU 一样慢）都动不了。
prefill 也只有 226 tok/s。首字延迟 0.08–0.18s（前缀缓存命中），所以**不是 SSE/传输层问题**。

**唯一能动的杠杆是 token 数量**：`PromptCharBudget(8192)` = 20,736 字符 ≈ 6,900 token ≈ 首字前 ~30s 的 prefill，
以及每轮各自的 prefill+生成。

### 3.2 生成并发（Ollama）

| 配置 | 2 次串行 | 2 次并发 | 加速比 |
| :--- | ---: | ---: | ---: |
| 默认（`NUM_PARALLEL=1`） | 3.7s | 4.2s | **0.87×** |
| `OLLAMA_NUM_PARALLEL=2` | 3.6s | 4.4s | **0.82×** |

**机制**：默认只有 1 个推理槽，第二个请求排队；开成 2 槽后两个请求争同一条内存总线，
KV cache 还被分成两半。两个都是负收益。

### 3.3 解析（版面检测）多进程

**CoreML 后端**（4 篇 PDF 旁路缓存）：

| 并发 | 总墙钟 | 每篇 |
| ---: | ---: | ---: |
| 1 | 8s | 8.0s |
| 2 | 17s | 8.5s |
| 4 | 32s | 8.0s |

**加速比 1.0×**：4 路墙钟正好等于串行 4×8s。原因见 §2.1——CoreML 编译全局串行。
代价实打实：每进程峰值 **836MB**，4 路要 3.3GB，而本机 swap 已用 11.3/12.3GB。

**纯 CPU 后端**（2 页/篇，6 篇）：

| 并发 | 每篇 | 相对串行 |
| ---: | ---: | :--- |
| 2 | 10.5s | **慢 1.75×** |
| 4 | 11.8s | **慢 2.0×** |
| 6 | 10.2s | **慢 1.7×** |

**比串行还慢**。这条与"加线程"的签名一致，指向同一机制（见 §5）。

### 3.4 解析多线程（intra-op）

同一页、同一输入，1/2/3/4 线程 = **1.9 / 3.7 / 5.4 / 7.4 s/页**。
**单调变慢**，而且不额外吃内存——这是"内存带宽受限"的教科书签名：
这个模型的算子是访存型，加线程只是让同一条总线更挤。所以默认固定
`DEFAULT_CPU_THREADS = 1`。

### 3.5 Laya 判定：线程池

sidecar 改双通道有界池（`decide` 并行、`parse` 串行）后实测：

| 配置 | 总墙钟（16 次判定） |
| :--- | ---: |
| 1 worker（对照） | **7.1s** |
| 2 workers | 7.5s |
| 4 workers | 7.6s |

**无加速**。把 state 拉大 4 倍（每调计算量 ×5）后仍然没有：4 次调用 1 worker 8.6s / 2 workers 9.9s
——所以**不是"每调固定开销主导"**。

### 3.6 Laya 判定：多进程（判别实验）

为了排除"同一进程内 ONNX 共享一个 intra-op 线程池导致串行"这一解释，做了这个实验：

| 配置 | 结果 |
| :--- | ---: |
| 单进程 16 次 / 1 worker | **7.1s** |
| 两个独立进程，各 8 次 / 1 worker | 每个 12.4s，总墙钟 **13s** |

两个进程**比单进程还差**。所以瓶颈**不在进程内的线程池**，而在整机共享的资源上，
且每进程多一份 1.2GB 权重让情况更糟。

### 3.7 Laya 判定：批量打分（尝试过并否掉）

**假设**：模型 fp32 1.2GB，每趟前向都要流一遍权重，那么一次前向覆盖多行就能摊薄。

**先验条件成立**：ONNX 图的 batch 维是动态的（`input_ids ['batch','seq']`、
`marker_pos ['batch','options']`、`qtype ['batch']`），所以批量在工程上可做。

**实测**（带标注数据，交替测量，各取最快；`rows=1` 是同一段代码跑两遍 → **噪声地板 0.97×**）：

| 行数 | 逐条 | 批量一次 | 加速比 | 选择一致 | max Δprob |
| ---: | ---: | ---: | ---: | :--- | ---: |
| 1 | 0.27s | 0.28s | 0.97× | ✓ | 0.0000 |
| 2 | 0.68s | 0.81s | 0.84× | ✓ | 0.0000 |
| 4 | 1.43s | 2.21s | 0.65× | ✓ | 0.0000 |
| 8 | 2.66s | 4.72s | **0.56×** | ✓ | 0.0000 |

复跑一次完全复现（0.58× / 0.56×）。

**数值上完全正确**：所有行填充到最长序列、填充被 attention mask 屏蔽，
8 行批量的选择与逐条**逐条相同、概率差 0.0000**——"填充对模型不可见"是被证明的，不是假设的。

**但性能是负的**，而且**成本是按 token 计的**：

- 逐条：2,202 token → 2.66s → **1.21 ms/token**
- 批量：同样的行 → 4.72s（填充后约 2,320 token）→ **2.03 ms/token（贵 1.7 倍）**

**没有东西可摊薄**：每行填充到最长宽度、attention 对宽度平方、批量的激活更大。
所以批量比逐条还慢，且随 batch 增大而更慢。

> 代码里 `LayaDecider.decide_many` 保留（`decide` 经由它，且组装/打分只有一份实现），
> 但 docstring 明确写着**实测更慢、不许当优化接上去**，并附上这张表。

## 4. 并发该用在哪（有效位置）

**判据是"这段工作在等 I/O，还是占资源"。** 本机实测：

| 阶段 | 耗时 | 性质 | 该并发吗 |
| :--- | :--- | :--- | :--- |
| 解析（版面检测） | 8.99s/篇（CPU，未缓存）→ **1.43s/篇**（CoreML + 会话缓存） | 访存/带宽受限 | ❌ 并发更慢（§3.3/§3.4） |
| Laya 判定 | 0.3–15s/次（随 state 长度） | 按 token 计的资源受限 | ❌ 并发无效（§3.5–3.7） |
| **嵌入（SiliconFlow HTTP）** | **0.2–1.05s/次**（3 次实测） | **纯网络等待** | ✅ **该并发** |
| upsert（qdrant） | ~0.05s | 网络 I/O | ✅ 该并发（但太小） |
| 生成（Ollama） | ~6.4 tok/s | 单槽排队 | ⚠️ 只有"少生成"有效 |

**已实现**：索引作业改为**异步 + 有界池**（`index_batch` 立即返回 job id、逐篇 `progress`、
`index_cancel` 可中断），额度 `indexBudget{Parse: 1, Write: 4}`——解析闸门只包住 `parse` 调用，
于是**文档 N 的嵌入/入库与文档 N+1 的解析可以重叠**。这才是 Go 并发在这里的正当用法。

> **诚实标注**：这条设计的**端到端收益尚未测量**。嵌入的延迟（0.2–1.05s/次）是实测的，
> "重叠能省下这部分等待"是推理。要落地结论需要一次带 `--no-cache` 的批量索引计时（做法见 §7.6，工具见 §9）。

另一个已确认的并发**正确性**前提（不是提速，但必须）：

- `sidecar.Client.Call` 写请求时**原本没有加锁**。macOS 的 `PIPE_BUF` 只有 **512 字节**，
  一个带 10k 字符 state 的 `decide` 请求远超它，写会被拆成多次 `write(2)`，
  两个并发 Call 就能**交错写入**，sidecar 收到坏行后回一个**与真实原因无关**的 parse error。
  已加独立 `writeMu`（不能复用 `c.mu`，否则写阻塞在满管道上会与读者互等）。
  用**变异测试**验证过：去掉锁后测试精确报出交错损坏。
- 同一会话被多个线程共享是**验过的**：4 线程并发 `decide` 无异常、答案一致
  （onnxruntime `Run` 线程安全这个假设不再只是文档上的一句话）。

## 5. 机制归纳：为什么都没提速

四条独立路径（解析多进程 1.0×、解析多线程单调变慢、Laya 多进程更差、Laya 批量 0.56×）
指向同一个结论：

> **这台机器上是一个已饱和的共享资源在限制，而不是核数。** 叠加在它之上的是
> **按 token 计算**的单趟成本。

具体表现：

- 加线程不额外吃内存却变慢 → 总线/带宽饱和；
- 加进程更慢 → 每进程多一份权重，进一步压总线与内存；
- 批量更慢 → 每 token 的成本不降反升（填充 + 二次方 attention）；
- **`num_gpu=0`（纯 CPU）比 Metal 还略快** → 连 GPU 路径也不是瓶颈所在。

**我无法从这些数据里分离的一点**：按 token 的成本中，"算子计算"与"访存流量"各占多少。
要 profiler 才能定。但**两者都推出同一个结论**——批量与并发都无效。

## 6. 参照：RAGFlow 的做法（它为什么能靠并发提速）

本机有一份 RAGFlow 的 Go 实现（`/Users/cbn/workspace/RAGFlow`），它的并发是**显式、有限、分阶段**的：

| 机制 | 位置 | 默认值 |
| :--- | :--- | :--- |
| 跨文档 worker 池 | `internal/ingestion/service/ingestion_service.go:628`（`startWorkerPool`） | `max_concurrent_workers = 2`（默认在 `internal/server/config/ingestor_config.go:35`、`conf/service_conf.yaml:100`） |
| 单文档按页并行 | `internal/deepdoc/parser/pdf/parser_concurrency.go:115` | `min(runtime.GOMAXPROCS(0), DeepDocConcurrency())` |
| **推理预算（信号量）** | `internal/deepdoc/native/inference_limit.go:33`（`slots chan struct{}`） | `deepdoc.inference_concurrency = 4`（默认见 `internal/server/config/deepdoc_config.go:33`） |
| 会话池 + 权重共享 | `internal/deepdoc/native/session_pool.go`、`session.go` 的 `weightCache` | 建一次、反复借还 |
| **intra-op 线程数** | `internal/deepdoc/native/session.go:36` | `intraOpThreads = 1`（**硬编码**） |
| 后端 | `internal/deepdoc/native/session.go:9` | **纯 CPU（by design）**；已核对：全仓无 `CoreML/CUDA/TensorRT/Dml` ExecutionProvider |
| OCR 批量 | `internal/deepdoc/parser/pdf/parser_ocr.go:25` | `recBatchNum = 16`（最多 16 行拼一次 Run） |

> 上表的行号已逐条 `sed` 核对过（引用错的行号比不引用更糟）。

**它为什么有效**：每会话只开 1 个 intra-op 线程 → 一次 Run 约吃 1 个核 → 4 个会话正好铺满 4 个核，
**并行度直接换成吞吐**。另外它把 OCR 的**最多 16 行拼成一次 Run**（`parser_ocr.go:25`）——
但那一条在我们这里是**反的**（§3.7），原因就是 §5 的"按 token 计的成本"。

**结论**：RAGFlow 的成功前提（CPU 算子可跨核摊开、无全局串行的编译步骤）在这台 Mac 上**不成立**。
照抄它的并发结构不会有收益，但它的**预算化思想**值得保留：
并发上限应该是一个**显式可配的数**，而不是"池子有多大就开多大"。

## 7. 未来可尝试的方向

按"打在哪、怎么验收"组织。**优先级从上到下**。

### 7.1 量化 Laya（int8）——最高优先

- **打在哪**：成本按 token 计、每 token 都要搬权重，而部署包给的是 **fp32（1.2GB）**，从未量化过。
  int8 能把访存砍到约 1/4，计算也可能受益。这是**唯一一条没试过、且直接打在真正瓶颈上**的路径。
- **怎么验收**：`scripts/eval_laya.py --bucket 400 --per-class 8`。当前基线
  **准确率 0.938（正例 1.000 / 负例 0.875）**，官方门槛是**域内宏平均 ≥85%**。
  量化后跑同一命令即可判断掉不掉分；顺带用 `scripts/bench_laya_batch.py` 量速度。
- **风险**：可能掉分；掉分就按官方建议"加数据 / 多训 1 epoch"，而不是硬上。

### 7.2 少判几次、判窄一点（策略旋钮，已有）

- `DefaultMaxStateChars = 10000`（≈2.3k token，填满约 15s/次）；`SCAMaxRounds`（Medium=3）；
  `ActionMaxTurns = 12`；复杂路径改成"每子问题各自 kbinfo"后，判定的 state 比并集小得多。
- **为什么这是有效杠杆**：既然按 token 计费，**减少 token 总量是直接的**。
  实测准确率在整个长度区间没有提升（370 tok 93.8%、2k tok 91.7%、8k tok 4/4，正例全程 100%），
  所以压 short 是"免费"的。

### 7.3 让生成更快：只有"少生成"

- 7 个旋钮全平（§3.1），所以**换更小的模型**或**更少的 token**是仅有的两条。
- 前缀缓存已经用上（`Loop.Warm` 预热 tool-plan 前缀，首字 0.08–0.18s）；
  `PromptCharBudget` 是 prompt 侧护栏。
- 值得试：把 Laya 已经能判的事情**别再让生成模型重复判**（当前结构已朝这个方向）。

### 7.4 给 Laya 上加速器（中级）

- 现在 `DEFAULT_PROVIDER_CHOICE = "cpu"`。但**先按 §2.1 的教训设计实验**：
  CoreML 的编译是全局串行的，只有在**会话缓存生效**之后才可能划算。
  Laya 的会话已经是进程级缓存 ✓，所以现在试 CoreML 的**前提已经具备**（当时布局模型不具备）。
- **验收**：`scripts/eval_laya.py` 对拍（两种 provider 的判定必须逐条一致）+ 计时。

### 7.5 解析提速：改输入而不是改并发

- 降 DPI / 降输入分辨率（直接砍 ANE/CPU 的工作量）；
- 换更小的版面模型；
- 已生效的最大一项仍然是**会话缓存**（6.3×），以及解析结果缓存（命中 0.07s vs 冷跑 8.43s）。

### 7.6 把"阶段重叠"量出来（廉价，且可能有收益）

- 设计已存在（`indexBudget{Parse:1, Write:4}`：解析串行、嵌入/入库并发重叠）。
- **待测**：一次带 `--no-cache` 的 100 篇批量索引，对比 `Write` 额度 1 与 4 的总墙钟。
  这是目前唯一"并发真的应该有用"的地方，**应该先证明再优化**。

### 7.7 不要重试的路（记录以免重复劳动）

- 解析多进程/多线程（§3.3、§3.4）；
- Laya 判定线程池 / 多进程 / 批量（§3.5–3.7）；
- Ollama 并发或 `NUM_PARALLEL`（§3.2）；
- 生成侧的 7 个旋钮（§3.1）；
- 指望 GPU/Metal 救场（`num_gpu=0` 反而略快）。

## 8. 未验证项（诚实清单）

1. **Laya 长上下文的官方门槛**：`decay_pp`（位置消融）与 Needle@32k 规定在
   `bench_length: [4000, 8000, 16000, 32000]` token 上测，本机跑不动
   （10.7k token 的判定 **9 分钟未完成**；部署包自己的 config 也写"CPU 单线程测 32000 要 30+ 分钟"）。
   已测到的只有 400 token 上的 **`decay_pp = 0.0pp`（门槛 ≤8pp）**。
2. **§4 的阶段重叠收益**（7.6）。
3. **按 token 的成本里，计算与访存各占多少**（§5，需要 profiler）。
4. **批量打分是否在别的机器上有收益**：本机 0.56×，但数值等价性已证明（Δprob 0.0000），
