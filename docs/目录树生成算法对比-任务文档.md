# 目录树生成算法对比 — 任务文档

> 目标：给**没有文件夹结构**的文档语料自动生成文件夹结构，把主流的几类算法都实现到同一接口，用同一把尺子测，选出最好的一种，并写清它好在哪、代价是什么。
>
> 依据：`internal/dirtree`（文档级目录树通道，2026-10-05 落地）的实测结果，以及「无文件夹结构语料生成层次结构」的方法综述（K-Means+HAC / LDA / 图聚类 / LLM 驱动 / 混合）。
> 相关：通道本身的设计见 `internal/dirtree/dirtree.go` 与 `route.go`；检索侧指标的定义见 `scripts/eval_doc_recall.py`。

---

## 0. 为什么要做这件事（起点是实测，不是猜测）

`fs` 通道已经能跑，但**路由本身几乎不工作**：

| 通道（24 道有证据的 dev 题，doc recall@8） | 文档召回 | 证据句召回 | 全部找齐 |
| :--- | :--- | :--- | :--- |
| keyword-doc（BM25 聚合成文档） | **0.938** | 0.986 | 20/24 |
| tree-doc（章节树聚合成文档） | 0.785 | 0.861 | 12/24 |
| fs-keyword（同一棵树，关键词定方向） | 0.795 | 0.924 | 12/24 |
| fs（laya 定方向 + 关键词兜底网） | 0.743 | 0.868 | 10/24 |
| **fs-pure（纯路由，无兜底网）** | **0.090** | 0.184 | 0/24 |

两个定位结论，决定了本任务的方向：

1. **0.743 不是 laya 挣来的**：去掉兜底网只有 0.090，114 个命中里 72 个来自关键词网。
2. **不是模型不行，是选项不行**。拿 3 个语义清晰的目录名单独测，laya 三次都选对（p = 0.49~0.73）；而真实目录树的根层决策只选对 **8/24**，关键词路由 **24/24**。真实目录名是两条被截断的新闻标题拼的（"How ego and fear fuelled the rise of art / How the conspirac"），六个选项的分数平得像 1.6 / 1.45 / 1.21 / 1.00。

所以：**先修目录结构本身，再谈路由**。本任务就是把"生成目录结构"这件事当成独立问题，系统地比一轮。

## 1. 目标与判定标准

### 1.1 目标

- 把 6 类建树算法**都实现到同一接口**，在同一语料、同一检索配置、同一批题目上比较；
- 选出最好的一种，并说明它的**代价**（耗时、依赖、是否需要模型、可解释性）；
- 结论要能反哺 `fs` 通道：结构变好之后，laya 路由是否随之变好（这是本任务的最终检验）。

### 1.2 怎么算"最好"（先定标准，避免事后挑指标）

**主指标**（检索质量，最重要）：

| 指标 | 含义 | 为什么是它 |
| :--- | :--- | :--- |
| `fs-keyword` doc recall@8 | 同一棵树、关掉 laya、纯关键词定方向时的文档召回 | **隔离出"树本身"的质量**，不含模型噪声 |
| `fs` complete@8 | laya 路由下，证据文档**全部找齐**的题数 | 多跳题要 2–3 篇，只有全找齐才算答得出来 |

**次指标**（结构质量 + 成本）：主题一致性、层次合理性、命名可读性、覆盖完整性、建树耗时、是否依赖外部模型、可解释性。

**判定规则**：主指标显著更好（doc recall@8 提升 ≥ 0.05）者优先；主指标持平时，取成本更低、可解释性更高的一种。

## 2. 待测方法（M0–M6）

所有方法输出**同一棵树**：`dirtree.Index`，节点为 `Node{Name, Summary, Children, Docs}`，叶子持有文档。**检索侧一行都不改**——这是能公平比较的前提。

| 编号 | 方法 | 实现要点 | 依赖 | 成本 | 可解释性预期 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **M0** | 递归 k-means（**现状基线**） | tf-idf 余弦 k-means 递归分裂，簇内代表文档标题命名 | 无 | 秒级 | 中：结构是数学的，名字是文档标题 |
| **M1** | K-Means + HAC | 先 k-means 得扁平簇，再层次凝聚（平均链接/余弦）成树；父节点由合并产生 | numpy / scipy | 低 | 中高：树状图的合并顺序可解释 |
| **M2** | LDA / hLDA 主题模型 | 文档-主题分布 → 主题即文件夹；层次靠 hLDA 或对主题再聚类；命名用主题词 | sklearn / gensim | 中（需调主题数） | 中高：主题词可读，但"文档为何属于此主题"是概率 |
| **M3** | 图聚类（Louvain / 标签传播） | kNN 相似度图 + 社区发现，递归对子图再做；命名用社区内中心文档标题 | networkx + python-louvain（**待装**） | 中（图构建 O(n²)，101 篇无压力） | 中：社区可读，边权重与阈值难解释 |
| **M4** | LLM 驱动两阶段 | ① 让本地 generator 给每篇生成标签/摘要/关键词；② 再让模型把标签分组并**用自然语言命名** | Ollama（`generator`） | **高**：101 篇 × 2 次调用 | 表面高、深层低（见 §4.3） |
| **M5** | RAPTOR 递归抽象 | 聚类 + 每层生成"簇主页"摘要，递归向上；摘要即节点 `Summary`（虚拟节点合成） | 聚类 + Ollama | 高 | 高：每层都有自然语言摘要作证据 |
| **M6** | 混合（粗聚类 + LLM 细化） | M1/M3 做粗粒度预聚类，只对簇调 LLM 做细粒度分层与命名 | 同上 | 中（LLM 调用随簇数而非文档数） | 中高 |

**实现位置（架构决定）**：聚类/主题/图算法需要 numpy、scipy、sklearn、networkx，放在 **sidecar（Python）**，新增 `sidecar/tree_build.py`；Go 侧只负责把返回的 JSON 树持久化到 `dirs.json` 并加载。理由与解析管线一致：重依赖留在 sidecar，内核保持薄。

**接口契约**：`fs.index` 增加 `method` 参数（默认 `kmeans`），取值 `kmeans / hac / lda / graph / llm / raptor / hybrid`；树落盘时 `Index.From` 记录方法名，保证任何一次评测都能说清测的是哪棵树。

## 3. 实验设计

### 3.1 数据与前置修复

| 项 | 现状 | 要做的 |
| :--- | :--- | :--- |
| 评测语料 | `eval/data-v12`：101 篇 MultiHop-RAG PDF、731 chunks、全部带 font_size | 固定不变，所有方法共用 |
| 题目 | `eval/dev.json` 24 道有证据题（8 道 null 题无证据，剔除）；结论在 `eval/test.json` 复测 | 固定不变 |
| **向量** | **只有 84/731 有向量**（建库时嵌入大部失败），语义相似度类指标测不了 | **先修嵌入再开始**；否则"主题一致性"只能用 tf-idf 近似，要在结论里写明 |

> ⚠️ 前置阻塞项：M1/M2/M3 的"主题一致性"需要文档向量。先把 `eval/data-v12` 的嵌入补齐（或明确降级为 tf-idf 余弦并标注）。

### 3.2 公平性约束（每次都必须满足）

- 同一 `branch` / `leaf_size` / `max_depth`（默认 6 / 4 / 4），逐一方法只改**建树算法**；
- 同一检索参数：`limit=8`、`beam=1`、`MinProbability=0`、兜底网 3 篇；
- 树建完先跑 `fs.status` 记录：节点数、叶子数、深度、`from`；
- 每题都跑三个变体：`fs-keyword`（树质量）、`fs`（含 laya）、`fs-pure`（纯路由）。

### 3.3 步骤

| 步骤 | 内容 | 产出 |
| :--- | :--- | :--- |
| S0 | 补齐嵌入；`sidecar/tree_build.py` 骨架；`fs.index` 的 `method` 参数 | 接口就绪 |
| S1 | M0 复测，作为对照基线 | 基线数字 |
| S2–S7 | 逐个实现 M1…M6，每个跑完整评测 | 每方法一张结果表 |
| S8 | 胜者在 `eval/test.json` + 用户真实 KB 上验证（真实 KB 有文件夹的，检查是否复现了用户的目录） | 泛化结论 |
| S9 | 用胜者的树重测 laya 路由：根层选对分支率是否从 8/24 提升 | **最终检验** |
| S10 | 结论写回本文档 §6，并把胜者设为 `fs.index` 默认方法 | 闭环 |

## 4. 评测维度

### 4.1 结构质量（离线，不跑检索）

| 维度 | 怎么测 | 记什么 |
| :--- | :--- | :--- |
| **主题一致性** | 同一叶子内文档两两余弦均值（有向量后）；全部叶子的加权平均 | 数值 + 最差的 3 个叶子 |
| **层次合理性** | 父节点的成员间相似度应低于其任一子节点内部（父更泛化）；抽样 10 组父子人工看 | 满足率 + 反例 |
| **命名可读性** | ① 人工 5 分制（2 人 × 20 个目录名）；② 自动：目录名与成员文档标题的词面重叠率 | 平均分 + 重叠率 |
| **覆盖完整性** | 文档总数 == 所有叶子文档数之和，无孤立点、无空节点 | 是否通过（应恒为通过，不通过即 bug） |
| **平衡性** | 叶子文档数的分布（是否有 1 篇 vs 30 篇的畸形叶子） | 最大/最小/中位数 |

### 4.2 检索质量（下游）

`scripts/eval_doc_recall.py -k 8 --cuts 3,5,8`，记录：

- doc recall@3 / @5 / @8（每个通道）
- fact recall@8（召回文档里是否真的有证据句）
- complete@8（全部证据文档找齐的题数）
- 中位耗时（建树耗时单记，检索耗时单记）

### 4.3 可解释性（单独打分，不折算进主指标）

必须区分两层，否则结论会自相矛盾：

| 层面 | 含义 | 传统聚类（M0–M3） | LLM 驱动（M4–M6） |
| :--- | :--- | :--- | :--- |
| **表面可解释性** | 目录名、摘要、层次、检索路径，人能不能看懂 | 低—中：名字是词或标题拼接 | **高**：自然语言命名 + 每层摘要 |
| **深层可解释性** | 为什么这篇文档在这？为什么检索选了这条路？ | 中—高：质心/树状图/主题词可数学追溯，但语义上说不清 | **低**：给出的理由是事后生成的，不等于真实决策依据 |

结论形态：**没有免费午餐**——LLM 方法"人能看懂"，传统方法"能数学追溯"。因此可解释性按 3 项计分：①命名可读性（人工分）②决策可追溯（能否给出证据：主题词 / 代表文档 / 摘要）③是否黑箱（是/否）。

> 对 `fs` 通道的实践含义：只要强制 laya 输出每层候选分数与选择理由，并把节点 `Summary` 作为证据保留，就能得到"路径可追溯"；但"为什么不是另一个分支"仍是黑箱。这一点要写进胜者方案的说明里。

## 7. 风险与注意

| 风险 | 说明 | 应对 |
| :--- | :--- | :--- |
| **嵌入缺失** | 731 chunks 只有 84 个有向量，语义类指标失真 | S0 先修；修不好就降级 tf-idf 并**在结论中标注**，不拿它下结论 |
| **LLM 成本** | M4/M5 需 101 篇 × 多次本地生成调用，Ollama 可能极慢 | 先跑 10 篇估算单篇耗时，超过预算就只做 M6（按簇调用） |
| **评测集偏窄** | MultiHop-RAG 是新闻短文，主题杂、多跳题跨簇，对"一个文档只属于一个文件夹"天然不利 | 结论里区分"方法好坏"与"语料是否适合"；M3/M6 的重叠簇能力单列观察 |
| **过拟合 dev** | 24 题调参容易过拟合 | 调参只在 dev，结论必须在 test 复现 |
| **树越深越好？** | 深度增加会让 laya 决策次数增加，错误累乘 | 固定 `max_depth=4`，不把深度当可调项 |
