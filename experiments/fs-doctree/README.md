# fs 通道：文档级目录树检索（PageIndex File System 式）

> 一句话：**语料级目录树，文档是叶子，每层用 laya-32k 判定下一个方向，只召回 doc，不做 chunking。**
> 跑起来的步骤与命令在 **[`RUN.md`](RUN.md)**；本文只讲方案与结论。

---

## 1. 它是什么

语料（101 篇文档）先被组织成一棵**目录树**——像文件系统那样：

```
语料库 (101 篇)
├── Walmart Cyber Monday / best October Prime Day      (14 篇)
│   ├── Amazon Alexa kids / smart home devices          (4 篇)   ← 叶子：4 篇文章
│   └── ...
├── ChatGPT everything you need to know / Kentucky      (13 篇)
└── ...
```

检索时从根出发，每到一个目录就问 laya-32k："这个问题指向哪个子目录？"，一路走到叶子，**叶子里的文档就是召回结果**。全程不返回、不排序、不选择任何 chunk。

它与仓库里另一个树通道 `internal/tree` 完全不是一回事：

| | `internal/tree`（旧） | `internal/dirtree`（本方案） |
| :--- | :--- | :--- |
| 树建在哪 | **每篇文档内部**（章节树） | **整个语料上**（目录树） |
| 叶子是什么 | 某篇文档里的一个章节 | **若干篇文档** |
| 方向怎么定 | 节点级 BM25 + beam | **laya-32k 逐层判定** |
| 召回单位 | chunk（passage） | **doc** |
| 是否 chunking | 是 | **否** |

## 2. 机制

### 2.1 建树（`internal/dirtree/dirtree.go`）

输入是 **101 篇文档**（不是 chunks）。层级两个来源，按可信度排序：

1. **真实文件夹**：源文件有几层目录就先按目录分层。语料全在一个文件夹里（评测集就是这样）就没有目录可用；
2. **内容聚类**：tf-idf 余弦 k-means 递归分裂，`branch=6 / leaf_size=4 / max_depth=4`。种子按 docID 间隔取而非随机——同一语料必须每次建出同一棵树，否则无法 diff、无法缓存。

**目录名不用词，用文档标题**：取簇内最具代表性的 2 篇文档标题拼成名字（"Walmart Cyber Monday / best October Prime Day"），词只留在 `Keywords`。目录名是给模型读的断言，`bankman·ftx·alameda` 这种词袋没人能判断。

### 2.2 方向判定（`internal/dirtree/route.go`）

每个非叶节点一次 `choice`：

- **options** = 子目录（`名字: 描述`）；
- **head** = 带问题的模板，4 个模板按 hash 轮换（与 `internal/agent/renderInstructions` 的约定一致：训练时是轮换的，钉死一个模板测出来的数对应不上部署）；
- **state** = 当前目录 + 已选路径；
- 拿回每个选项的分数后按 **beam** 保留前 N 个方向，第二个方向不额外花钱；
- 没有模型时整层改关键词排序，并在 trace 里标 `reason: keyword`——**不冒充模型决策**。

### 2.3 下降顺序

**最佳优先**：先把排名第一的分支一路走到叶子，再回头开后面的分支。逐层下降会在预算耗尽前一步叶子都没摸到（branch=3 时实测路由返回 0 篇，全靠兜底）。

结果顺序 = 路由打开顺序（不是置信度）。置信度逐层相乘会随深度衰减，按它排序会把槽位全给**最浅**的分支——也就是最不具体的那条路。这条 bug 实测：beam=2 得 0.10，beam=1 得 0.66。

### 2.4 召回单位

`fs.search` 返回 `doc_id + 目录路径 + 来源`，**`chunks` 字段恒为 0**。文档级 BM25 只用于三处：叶子内排序、无模型时的整层排序、关键词兜底网；**从不替代路由决策**。

兜底网的槽位是**预留**的，不是追加后截断——追加再截断等于路由找到 8 篇时把网整个扔掉，恰好在最需要它的时候没有它。

### 2.5 三种宽度（`Branches` / `Beam` / `Slots`）

证据在语料里是分散的（每题平均落在 **2.29 个叶子**上），所以"走几条路"是这个通道最要紧的旋钮。三种加宽方式**不是一回事**，全部实现并分别测过：

| 旋钮 | 在哪加宽 | 一次决策的性质 |
| :--- | :--- | :--- |
| `beam` | 每一层都保留 N 个方向 | 每层都多选，路径数随深度指数增长 |
| `branches` | 只在根层选 N 个方向，各自走到自己的叶子 | 一次决策定 N 个终点 |
| `slots` | 先把问题拆成 N 个子问题（槽表），每个槽各搜一遍整棵树 | 问题被拆开，每槽一条完整路径 |

### 2.6 可解释性（`explain`）

这个通道天然可解释——它召回的是"某个目录下的某篇文档"，路径本身就说得清。但**裸分数说不清**：`39.72` 不告诉读者这个目录是因为命中 `pixel` 还是命中 `the` 才赢的。所以 `fs.search` 加了 `explain`（默认关）：

| 输出 | 内容 |
| :--- | :--- |
| `trace.steps[].options[].matched` | 每个候选目录赢下这一层的**查询词**与各自贡献分（前 3 个） |
| `hits[].matched` | 每篇文档命中的查询词与贡献分 |
| `hits[].why` | 一句话：`由第 2 个分支召回；命中 3/28 个查询词（llm、kids、amazon），BM25 32.2；目录 语料库 › …` |
| `hits[].evidence` | 文档里命中词最多的那个段落（截断 240 字） |
| `trace.notes` | `未开启的分支：NFL Fantasy… (BM25 8.5)；…` —— 4 分支时那 2 个为什么没开 |

三条设计约束：

1. **归因来自文档，不来自目录**。目录只是两条截断标题拼的名字，没有自己的文本；说"这个目录命中了 amazon"是在对一个不能命中任何东西的对象下断言。所以 `matched` 是**目录内最强文档**的命中词。
2. **`explain` 是纯输出**，任何决策都不读它。已验证：`fs-br4-kw` 与 `fs-br4-kw-explain` 在 24 题上 **24/24 文档列表完全相同**，doc@8 都是 0.8542。
3. **`evidence` 由调用方（store）补**，树里不存正文——目录只有文档 id 和名字，把语料副本塞进 `dirs.json` 是另一回事。取段落用的是与召回同一个尺子（命中词数），用另一套排序挑出来的段落解释的就不是这次召回。

它顺手暴露了真问题：上面那题查询有 28 个词，4 个分支各自只命中 3 个，第 4 个分支是靠 `article、suggest、large` 这种噪声词开的——**可解释的价值在这里**，不开 `explain` 这个缺陷看不出来。

### 2.7 RPC

| 方法 | 作用 |
| :--- | :--- |
| `fs.index` | 建树并落盘到 `dirs.json`（参数 `branch` / `leaf_size`） |
| `fs.status` | 树形结构：节点数、叶子数、深度、`from`（path/cluster/mixed）、顶层目录名 |
| `fs.search` | 路由检索。参数 `limit` / `beam` / `branches` / `slots` / `max_steps` / `min_probability` / `candidate_k` / `no_fallback` / `fallback_limit` / `no_laya` |

`no_laya`（关模型）、`no_fallback`（关兜底）是为评测准备的消融开关，用来把"树错了"和"模型错了"分开。

## 3. 实测结论

两套口径，24 道有证据的 dev 题。

### 3.1 结构容量（不看路由，只看树装不装得下答案）

`eval/oracle_capacity.py`，预算 8 篇文档（[数据](results/oracle-capacity.json)）：

| 指标 | 值 | 含义 |
| :--- | :--- | :--- |
| gold 文档在某个叶子里 | **1.000** | 树没把语料切丢，问题不在建树 |
| **单路径上限（只进 1 个叶子）** | **0.510** | 路由再准也只能拿回一半证据 |
| 多分支上限（≤2 个叶子） | 0.868 | |
| 多分支上限（≤4 个叶子） | **1.000** | 结构容量完全够 |

**单路径下降已被证伪**：天花板 0.510，而 BM25 基线 0.938。在这条路上"让模型选得更准"没有任何意义。

## 4. 三个已经定死的结论

### 4.1 加宽有效，但只在根层加宽有效

- **根层分叉（`branches=4`）是唯一真正赚到的改动**：0.795 → **0.854**（+0.059），且几乎不花时间（0.16s）。
- **每层加宽（`beam=3/4`）反而更差**：0.740 / 0.747，都低于 beam=2 的 0.795。路径数随深度膨胀，多出来的分支排在后面、拿不到槽位，还挤掉了好的。
- **纯路由口径下加宽是亏的**：`br4-kw-pure` 0.563 < 单路径无兜底 0.802。加宽的收益几乎全部来自"兜底网兜得更准"，不是来自走到的叶子更多。

### 4.2 槽表（deep research 式）在这棵树上是净损失

- 单独用：`slots3-kw` 0.701、`slots4-kw` 0.733，都低于不拆的 0.795。
- **原因**：拆开之后每个子问题的词项变少，关键词匹配变弱；而每个槽各带一份兜底网，合并时排在各自末尾，基本被浪费。
- 与分支叠加（`slots2/3 + branches4`）：0.781 —— 好于单独槽表，仍低于不加槽表的 0.854。
- 带 laya 的槽表是灾难（0.083）：每个槽都在做一次很差的路由。

### 4.3 laya 的每一次判定都是净损失

对照（同树、同参数，只换"谁决定方向"）：

| 配置 | laya | 关键词 |
| :--- | :--- | :--- |
| 单路径 | 0.743 | 0.795 |
| 根层 4 分支 | 0.771 | **0.854** |
| 槽表 3 | 0.083 | 0.701 |
| 单路径无兜底 | 0.090 | 0.802 |

差距来自选项本身：真实目录名是两条被截断的新闻标题拼的，根层六个选项的分数平得像 1.60/1.45/1.21/1.00。拿三个语义清晰的目录名单独测，同一个模型三次都选对（p = 0.49~0.73）。**不是模型不行，是喂给它的断言不行。**

缩减候选（`candidate_k`）——先用关键词取 top-K 再让模型选——确实把纯路由从 0.090 提到 0.601，但那只是**削弱它的破坏力**：极限就是 0.802（完全不让它选），而 `candN-kw` 与关键词路由数字完全相同，证明缩减对关键词路由是恒等操作。

## 5. 判定：不配当主召回

README 里立的停止条件是"多分支之后仍打不过 `keyword-doc` 的 0.938 就降级为辅助通道"。**条件成立**：最好的树结果是 0.854，差 0.083。

树结构本身没问题（容量 1.000，证据一篇没丢），卡住的是两件事：

1. **目录名是坏断言** —— 两条截断标题拼出来的名字，模型读不出方向，人也一样；
2. **加宽的收益被兜底网吃掉** —— 去掉网，加宽反而更差（0.563 vs 0.802），说明路由走到的叶子并不比 BM25 的全库排序更准。

还值得试的（按期望值排序）：

1. **让 laya 读文档标题而不是目录名**（§4.3 的直接推论，唯一指向"模型其实能用"的方向）；
2. **给槽表单独一份全局兜底网**，而不是每个槽各带一份（§4.2 的直接推论）；
3. 目录描述改用生成模型写（`generator` 已可用：ollama `qwen3-vl:4b`）；
4. 多跳跨簇仍需在"一次决策选多个终点"之外解决——`branches` 只在根层分叉，第二跳若在同一分支内仍会丢。

不值得再试的：单路径下降（上限 0.510）、每层加宽 beam（实测更差）、候选集缩减（§4.3）、用 laya 做槽表路由（0.083）。
